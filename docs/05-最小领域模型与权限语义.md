# 最小领域模型与权限语义

- **文档状态**：MVP-1 领域基线与下一阶段运维模型入口
- **版本**：0.5
- **日期**：2026-08-12
- **目的**：把“Linux HOST + SSH 只读事实 + 确定性图草稿 + 人工管理 + 可选 Agent 建议”落成最小、可验证的数据边界。

## 1. 第一性原理

MVP-1 只需要回答四件事：

1. **外部实际发现了什么？**——HOST、Docker/Compose、文档事实与稳定外部身份。
2. **我们凭什么这样显示？**——来源、观察时间、扫描运行、哈希与脱敏状态。
3. **当前图是草稿还是用户已确认的投影？**——确定性映射、Agent 建议和用户决定分层。
4. **谁可以查看和修改本地投影？**——当前只有工作区所有者。

MVP-1 不需要回答“哪个项目 Agent 对结果负责”“多个项目如何共享权限”或“允许执行什么外部动作”。这些是 Post-MVP 问题，不能提前变成必建实体、表或 API。

核心不变量：

> 外部事实不等于本地投影；确定性映射不等于用户决定；Agent 建议不等于事实；本地确认不等于外部对象被创建或修改。

## 2. MVP-1 层级模型

```text
Workspace（单一所有者）
├── Host（一个 Linux TARGET_HOST）
│   └── DiscoveryRun[]
│       └── EvidenceItem[]（含白名单文档的脱敏证据）
├── ProjectionDraft
│   ├── Project[]
│   ├── Entity[]
│   ├── EntityRelation[]
│   └── CanvasLayout
├── Optional Agent Assistance
│   ├── ProjectProposal[]
│   └── OnboardingSession
└── ProjectionVersion[]（用户确认）
```

项目是当前图中的业务组织单元；HOST、Compose 项目、服务/容器、网络、卷、端口和文档是可视化实体。业务统筹 Agent / 项目 Agent、工作流、共享组、访问授权和外部动作不属于 MVP-1 必建领域。

### 2.1 单一所有者边界

MVP-1 只有一个 `Workspace.owner_id`。所有业务 API、SSE、HOST 登记、扫描、草稿修改、模型配置、导出和删除均要求有效所有者会话。多人协作、组织角色和复杂 RBAC 后置。

### 2.2 下一阶段运维层级

MVP-1 的 Workspace、Host、Evidence、Project 和 ProjectionDraft 继续作为现有兼容模型。下一阶段在其上增加运维语义：

    Business
    └── TechnicalProject
        └── ProjectTarget
            ├── HOST
            └── Deployment

服务器上直接观察到的是 DeploymentCandidate 和资源 Evidence；Business、TechnicalProject 与 ProjectTarget 都需要本地确认。CodeWorkspace 不进入运维核心模型，部署只保留可观察的版本元数据。

## 3. MVP-1 最小实体

| 实体 | 必要字段 | 说明 |
|---|---|---|
| `Workspace` | `workspace_id`, `owner_id`, `created_at` | 远程部署实例的单一所有者技术根 |
| `OwnerSession` | `session_id`, `owner_id`, `expires_at`, `revoked_at?` | 互联网访问的所有者会话 |
| `Host` | `host_id`, `display_name`, `address`, `port`, `ssh_user`, `credential_ref`, `credential_kind`, `host_key_fingerprint?`, `host_key_state`, `status` | 通过 SSH 登记的 Linux TARGET_HOST |
| `SecretRef` | `credential_ref`, `kind`, `created_at` | SSH 密码、SSH Key/模型 Key 的服务端引用描述，不含秘密本体 |
| `DiscoveryRun` | `run_id`, `host_id`, `state`, `submitted_at`, `started_at?`, `finished_at?`, `failure_code?` | 一次固定只读发现任务 |
| `EvidenceItem` | `evidence_id`, `run_id`, `kind`, `external_id`, `source`, `observed_at`, `sha256?`, `redaction_state`, `metadata_json` | Docker/Compose 事实及白名单文档的脱敏证据；不保存完整文档正文 |
| `Project` | `project_id`, `label`, `projection_state`, `source_refs[]` | 本地项目容器；可来自确定性候选或用户确认 |
| `Entity` | `entity_id`, `kind`, `source`, `external_id`, `observed_at`, `projection_state` | 可视化对象的稳定引用 |
| `EntityRelation` | `relation_id`, `from_id`, `to_id`, `kind`, `source_refs[]`, `projection_state` | 有来源的关系边 |
| `ProjectionDraft` | `draft_id`, `discovery_run_id`, `base_revision`, `state`, `updated_at` | 可编辑图草稿；先由规则生成，再接收人工/Agent 补丁 |
| `ProjectionVersion` | `version_id`, `revision`, `confirmed_by`, `confirmed_at`, `snapshot_ref` | 用户确认后的不可变本地投影 |
| `CanvasLayout` | `layout_id`, `scope`, `revision`, `positions_json` | 只保存最终节点位置；缩放/悬停留在前端 |
| `IgnoreRule` | `rule_id`, `host_id`, `fingerprint`, `state`, `created_at` | 归档/忽略后避免重扫自动恢复 |
| `ModelProvider` | `provider_id`, `base_url`, `model`, `secret_ref`, `state` | OpenAI Chat Completions 兼容配置 |
| `ProjectProposal` | `proposal_id`, `draft_id`, `evidence_refs[]`, `confidence`, `state` | 可选 Agent 归类/关系建议 |
| `OnboardingSession` | `session_id`, `draft_id`, `state` | Agent 问题、用户回答和建议补丁 |
| `ConnectionTest` / `ModelProviderTestRun` | `test_id`, `state`, `error_code?`, `started_at/created_at` | 连接与模型配置的阶段专属测试记录 |
| `MutationReceipt` | `resource_kind`, `resource_id`, `idempotency_key`, `request_sha256`, `response_json` | 分阶段保存可重放的修改回执，不建设通用任务平台 |
| `AuditEvent` | `event_id`, `actor_id`, `kind`, `target_ref`, `occurred_at`, `summary` | 最小脱敏审计摘要 |

### 3.1 MVP-1 实体类型

`Entity.kind` 首批只允许：

```text
host
compose_project
service
container
image
network
volume
port
document
```

工作区和项目使用独立实体，不塞进 `Entity.kind`。未知 Docker 对象可以保留受控 `unknown`，但不得因为 Agent 描述随意创建新的数据库类型。

### 3.2 MVP-1 关系类型

首批关系只允许当前事实能够支持的少量类型：

```text
contains
deploys
depends_on
connects_to
mounts
exposes
uses_image
documents
```

`responsible_for / delegates / controls / approves` 等责任或控制关系属于 Post-MVP。一个关系若没有明确事实来源，应保持建议状态或由用户创建为本地声明，不能显示成已发现事实。

### 3.3 下一阶段实体与关系

| 实体 | 作用 |
|---|---|
| Business | 跨 TechnicalProject 的业务语义分组和策略范围 |
| TechnicalProject | 一个 Project Agent 的运维责任边界 |
| DeploymentCandidate | 多 Provider Evidence 归并出的待确认部署候选 |
| Deployment | 用户确认后的稳定部署/运行单元，不直接保存单值 project_id |
| ProjectTarget | TechnicalProject 与 Deployment/HOST/adapter 的本地目标绑定 |

Deployment 的稳定身份优先使用 host_id + provider_kind + external_id。ProjectTarget 保存目标级适配器、能力、审批和最近观察引用；它是关联与配置记录，不是权限授予本身。

候选生命周期为：

    observed → unassigned → linked → confirmed → stale / ignored

Docker/Compose、systemd、PM2、端口/进程等 Provider 可以为同一个 Deployment 追加 Evidence。单个 Provider 不可用只降低 coverage，不改变 HOST 的 connection_ready。

## 4. 事实、映射、建议和决定的分层

| 层 | 记录 | 产生者 | 可变性 |
|---|---|---|---|
| 外部事实 | `EvidenceItem` | SSH 发现器/文档提取器 | 单次扫描内不可改；新扫描追加新事实 |
| 确定性映射 | `ProjectionDraft` 初始节点与边 | 规则映射器 | 可在草稿中修改；必须引用事实 |
| Agent 建议 | `ProjectProposal / onboarding patch` | 模型服务 | 可采用、拒绝、过期；不能直接发布 |
| 用户决定 | 草稿补丁与 `ProjectionVersion` | 所有者 | 产生新修订/版本，不改写旧确认版本 |

### 4.1 外部身份与本地身份

```text
source + external_id      外部稳定身份
entity_id / project_id    本地稳定身份
discovery_run_id          本次观察批次
projection_state          discovered | draft | confirmed | stale | archived
fact_state                observed | missing | conflicting
```

同一个 `(source, external_id)` 只对应一个本地 `entity_id`。重新扫描发现对象消失时，保留本地身份并标记 `missing/stale`；不把它等同于用户归档，也不自动删除已确认投影。

### 4.2 来源要求

每个已发现节点与关系至少包含：

```text
source_refs[]
observed_at
discovery_run_id
redaction_state（适用时）
```

Agent 建议额外包含 `reason / confidence / evidence_refs[]`。用户创建的本地声明包含 `confirmed_by / confirmed_at`，并明确标记为 `user_declared`。

## 5. 图草稿与版本约束

1. `evidence_ready`（旧兼容）、`discovery_complete` 或 `discovery_partial` 后，由确定性映射器立即产生 `ProjectionDraft`，不得等待模型；`discovery_unavailable` 不产生草稿或 Agent 会话。
2. 无法明确归类的资源进入 `unassigned`，不由规则猜测。
3. Agent 只对现有草稿产生建议层或补丁，不替换基础草稿。
4. 草稿修改带 `base_revision`；API 使用 `If-Match`，冲突返回 `412`。
5. 用户确认产生新的 `ProjectionVersion`；旧版本保持不可变。
6. `IgnoreRule` 只影响本地候选显示，不删除事实或外部对象。
7. `CanvasLayout` 只保存最终位置与修订，不保存悬停、缩放或临时动画状态。

## 6. MVP-1 权限语义

当前权限判断只有三层：

```text
是否存在有效 OwnerSession？
→ 请求是否属于该 Workspace？
→ 请求是否属于 MVP-1 允许的本地操作或固定只读发现？
```

允许的操作：

- 读取工作区、HOST、发现、证据、图草稿和已确认投影；
- 登记 HOST、提交 SSH 密码、SSH Key/模型 Key 到服务端秘密存储；
- 确认主机指纹、启动固定只读扫描；
- 修改/确认图草稿、布局、归档和忽略规则；
- 配置模型并与辅助会话交互；
- 导出或删除工作区/HOST/项目数据。

禁止的操作：

- 任意 SSH 命令、自动提权和 TARGET_HOST 写入；
- Docker/项目文件修改或删除；
- 外部暂停、取消、改向、批准或执行；
- 跨用户共享和未认证公开读取；
- 把秘密本体写入 SQLite、API 响应、SSE、日志或 Agent 上下文。

MVP-1 不建立 `SharedGroup / ProjectMembership / AccessGrant / Capability / ActionRequest`。保留名字或空表也会造成虚假的实现承诺，因此到对应 Post-MVP 阶段再设计。

### 6.1 下一阶段 Project Agent 权限

下一阶段不向 Agent 暴露任意 HOST Shell。项目 Agent 的有效能力取以下约束的交集：

    全局硬限制
    ∩ BusinessPolicy
    ∩ ProjectAgentPolicy
    ∩ ProjectTarget.capabilities
    ∩ 本次审批结果

Project Agent 对项目范围内的结构化观察拥有按需读取权，工具必须显式指向 ProjectTarget。业务策略可以收紧项目权限；跨项目私有数据需要显式授权。写入、重启和部署动作仍需独立规格、回执、重新观察和回滚/补偿。

## 7. HOST 与投影生命周期

```text
host_registered
→ fingerprint_fetching
→ host_key_unverified
→ host_key_verified（用户确认）
→ connection_checking
→ connection_ready
→ discovery_running
├─ evidence_ready（旧兼容） | discovery_complete | discovery_partial
│   → draft_ready
│   → needs_user_review
│   → confirmed | edited | rejected | archived
│   → projection_published
└─ discovery_unavailable（无草稿、无 Agent 会话）
```

Agent 辅助从 `draft_ready` 并行开始：

```text
proposal_generating
→ proposal_ready | needs_user_input | model_unavailable | proposal_invalid
```

后两种失败不改变 `draft_ready`，也不阻止人工确认。

## 8. MVP-1 实现约束

首版只建以下持久化分组：

```text
workspace/auth/secret
host/connection
discovery/fact/document
project/entity/relation
projection_draft/version/layout/ignore_rule
model_provider/proposal/onboarding
stage_run/idempotency_receipt/audit/schema_migration
```

`DiscoveryRun`、`ConnectionTest`、`OnboardingSession` 和 `ModelProviderTestRun` 分别拥有自己的状态与失败语义；MVP-1 不建立没有当前消费者的通用 `Job / JobAttempt` 表。

当前不建：

```text
shared_group/access_rule
workflow/run/operation
action_request/action_receipt
project_agent/responsibility_contract/project_pulse
knowledge_grant/delegation
```

新增表的门槛是：现有实体无法表达一个已进入当前阶段的真实用例，而不是“未来也许会用”。

## 9. Post-MVP 扩展顺序

只有 MVP-1 通过真实样本验证后，再按瓶颈依次评估：

1. 多 Provider 部署发现、DeploymentCandidate、Deployment 和 ProjectTarget；
2. 服务器资产与最近观测页面；
3. 项目 Agent、责任契约和范围化项目脉搏；
4. 共享资源与知识权限；
5. 一个真实、可回执、可重读验证和可回滚/补偿的外部动作；
6. 多 HOST、多用户与跨项目协调。

后续对象的参考语义见 `docs/11`，但必须在进入对应阶段时重新验证，而不是直接把愿景模型迁入 MVP-1。
