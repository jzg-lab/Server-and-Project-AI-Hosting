# 部署与架构维护指南

> 状态：架构审计与渐进维护基线
> 日期：2026-08-14
> 正式部署操作入口：[`../deploy/README.md`](../deploy/README.md)

## 1. 目的

本文件回答两个问题：当前系统实际由什么组成，以及后续如何在不删除现有功能、数据和兼容契约的前提下整理结构。它不是第二份部署命令手册；所有正式上线命令以 `deploy/README.md` 为准。

## 2. 事实、推测和待验证项

### 已确认事实

- 后端是 Rust/Axum + SQLx/SQLite 的模块化单体，不是完全无结构的原型。
- 前后端由同一 Rust 进程提供，正式部署通过 Caddy 暴露 HTTPS。
- APP_HOST 保存 SQLite、FileSecretStore 和 SSH 状态，通过 OpenSSH 只读访问 TARGET_HOST。
- `backend/src/api.rs` 是清晰的组合根；`ssh.rs`、`discovery.rs`、`secrets.rs`、`storage.rs` 已形成可保留边界。
- 后端最大的职责集合是 `projection.rs` 和 `m1.rs`；前端最大的职责集合是 `app.js`。
- `frontend/data-source.js` 已把 Mock 与 HTTP 传输隔离，当前不需要重做。
- 当前实现和定向测试均已确认：SSH/Linux 身份成功即 `connection_ready`；Docker 缺失或权限不足是后续发现结果。
- 现有 Docker Compose 发布包已包含 app、Caddy、健康检查、持久卷、非 root 运行、备份、恢复、升级和回滚脚本。

### 有依据的工程判断

- 当前维护瓶颈是职责集中、状态语义混用和行为测试不足，不是缺少微服务或大型基础设施。
- 保持模块化单体、SQLite 和原生前端的成本最低；先收紧内部边界比换框架更可靠。
- 大文件本身不是删除或重写理由。只有在测试锁住行为后，按职责机械拆分才会降低长期成本。

### 待验证项

- 同一 HOST 并发发起两个连接测试时，最终状态和回执是否会相互覆盖。
- 进程在 `fingerprint_fetching` 或 `connection_checking` 中断后，HOST 是否会长期停留在过渡状态。
- 一次 HOST 更新是否会由 handler 和认证中间件重复发布 SSE 事件。
- Linux Docker 实机上的首次证书、登录、恢复和升级回滚仍需发布环境验收；Windows 上的 Compose 静态解析不等于该验收。

## 3. 正式运行拓扑

```text
Browser
  -> HTTPS / SSE
Caddy on Linux APP_HOST
  -> Docker internal network
Rust/Axum modular monolith
  -> frontend static files
  -> REST + SSE
  -> SQLite WAL
  -> FileSecretStore
  -> OpenSSH read-only discovery
       -> Linux TARGET_HOST
```

环境只有三种，不得混称：

| 环境 | 用途 | 进程管理 | 是否正式交付 |
|---|---|---|---|
| 本地开发 | 编译、单元和集成测试 | `cargo run` | 否 |
| Windows 验收 | UI、真实连接和临时可用性验证 | 本地进程或临时 PM2 | 否 |
| Linux 发布 | 正式互联网运行 | Docker Compose `restart: unless-stopped` | 是 |

PM2 解决的是 Windows 测试进程退出后的临时持续运行问题。它不进入 Docker 镜像、Compose、生产监控或正式部署文档。

## 4. 连接与发现的领域边界

第一性问题是“应用能否访问服务器”，而不是“服务器是否安装 Docker”。因此：

```text
HOST connection
  = network reachable
  + SSH authenticated
  + Linux identity readable

optional discovery
  = Docker / Compose / systemd / PM2 / process / documents / other facts
```

连接成功后，附加发现可以分别为可用、未安装、权限不足或执行失败。前端和 API 应分别表达 `connection` 与 `last_discovery`。现有 `HostStatus` 中遗留的 Docker 枚举暂不删除，以免破坏 OpenAPI、历史 JSON 或数据库兼容；新代码停止依赖这些值，并通过后续 additive migration 渐进拆开。

## 5. 当前目录职责

```text
backend/
  src/                 Rust 应用、领域用例、适配器和 HTTP 入口
  migrations/          只追加的 SQLite 迁移历史
  tests/               M0-M4 跨层验收
frontend/
  index.html            薄加载入口
  app.js                当前 UI composition root，待渐进拆分
  data-source.js        Mock/HTTP 传输边界
  generated/            OpenAPI 生成类型
  tests/                前端契约与纯函数测试
deploy/                 唯一正式 Linux Compose 发布包
docs/                   产品、架构、部署和验收主记录
data/                   本地运行数据与秘密，不进入 Git
artifacts/              验收证据，不作为运行时源代码
scripts/                本地里程碑验证入口
```

不建议仅为了目录整齐移动所有文件。目录调整必须跟随真实职责边界，并保持加载顺序、路由、生成类型、迁移和测试入口不变。

## 6. 后端维护路线

### P0：先修可靠性语义

- 为连接和发现建立独立行为测试，同时保持当前外部 JSON 兼容。
- 覆盖同 HOST 并发连接、同幂等键重放、进程中断恢复和 SSE 精确事件数量。
- 将连接测试最终 HOST 状态和 `connection_tests` 回执放进同一事务；外部 SSH I/O 仍在事务外。
- 对每个 HOST 使用轻量原子 claim、条件更新或进程内互斥，避免旧尝试覆盖新结果。
- 启动时把未完成连接尝试归一为可解释状态，不自动删除凭据。

### P1：机械拆分 `m1.rs`

建议内部结构：

```text
m1/
  mod.rs                 保持现有 handler 重导出
  host_store.rs          HOST CRUD 和状态存取
  credentials.rs         SecretRef 与凭据描述符
  connection.rs          host key、指纹和连接状态机
  discovery_runs.rs      发现任务编排与恢复
  evidence_store.rs      证据和审计持久化
```

每次只移动一个边界，并运行 M0/M1、OpenAPI diff 和迁移检查。不要在机械拆分时顺带更名 DTO、表或错误码。

### P2：拆分 `projection.rs`

```text
projection/
  mapping.rs             Evidence -> Graph 纯映射
  drafts.rs              草稿、确认、布局、归档和 undo
  read_models.rs         global/project/bootstrap 读模型
  agent_patch.rs         Agent patch 的窄边界
  repository.rs          投影领域 SQL
```

读模型应直接从 typed HOST 数据生成 API 字段和展示摘要，避免从“IP 地址”“SSH 端口”等展示文本反解析业务字段。将通用请求元数据、时钟、摘要和幂等 helper 移出 `model_provider.rs`，使确定性 M2 不再依赖可选 M3 的错误类型。

### P3：下一阶段部署目录

只有 Provider 部分成功语义和真实样本稳定后，再按以下职责增加模块：

    discovery/providers/        Docker、Compose、systemd、PM2、进程/端口
    discovery/candidates.rs     DeploymentCandidate 归并与覆盖范围
    catalog/deployments.rs      Deployment 稳定身份与观察历史
    catalog/project_targets.rs  TechnicalProject 与 Deployment/HOST 关联
    projection/hosts.rs         global/hosts 读模型

Deployment 不直接保存单值 project_id；ProjectTarget 是本地目标关联。每个 Provider 的失败都要留在 coverage 和 warnings 中，不得把 HOST 降级为 SSH 失败。

### P4：小范围公共设施

- 统一 workspace ID、request ID、时间和摘要生成。
- 抽取窄的幂等存储 helper，但保留现有领域表，不构建通用 ORM/Repository 框架。
- HTTP 写事件选择唯一发布者；后台任务继续由任务编排器显式发布。
- 把测试公共装配放入 `backend/tests/support/`，保留纵向验收入口。

## 7. 前端维护路线

### P0：先补真实交互回归

现有测试主要约束 `data-source.js` 和源码文本，不能证明交互真的可用。先建立可重复浏览器测试，覆盖：

- 登录与刷新恢复；
- 点击画布服务器切换服务器操作上下文；
- 节点拖拽和画布空白平移不互相误触；
- 布局保存后刷新仍恢复；
- 通过界面保存密码、确认指纹、SSH 连接成功；
- SSH 成功而 Docker 缺失时仍显示 HOST 已连接；
- 401、SSE 刷新、过期异步响应和秘密不回显。

### P1：先提取纯函数和显式状态动作

- 提取路由解析、HOST 状态映射、图几何、节点防重叠、DTO 到 view model 映射。
- 将内置 Fixture 移到独立模块，保留 `file:` 和 `?data=mock` 行为。
- 用显式 action/reducer 整理导航、HOST 选择和画布状态；渲染函数只读状态。

### P2：按纵向功能拆分

```text
frontend/
  app.js                 组合与启动
  state/                 actions 和状态更新
  features/hosts/        凭据、指纹、连接状态机和服务器资产页
  features/deployments/  Provider 能力、DeploymentCandidate 和 ProjectTarget 上下文
  features/canvas/       几何、节点拖拽、空白平移和布局持久化
  features/projection/   草稿编辑和确认
  features/agent/        可选 Agent 建议
  views/                 world/hosts/resources/workflow 渲染
  data-source.js         保持现有传输边界
```

先拆 HOST 管理，再拆通用画布，最后拆三类视图和 CSS。保持 `index.html` 的薄入口和视觉基线；不一次性替换 `innerHTML` 渲染模型。

## 8. 暂不采用的方案

目前没有证据支持以下成本：

- 微服务、PostgreSQL、Redis、消息队列、图数据库；
- React/Vue/Svelte 全量重写、Redux、微前端或独立前端服务；
- Canvas/WebGL 替换 SVG；
- 通用 DDD/DI/Repository 框架、事件溯源、插件 ABI 或通用任务平台；
- 删除 Fixture、历史迁移、遗留枚举、生成类型、设计依据或真实数据。

重新评估的触发条件应是可测量事实，例如多副本部署、跨节点任务、SQLite 锁竞争、独立升级或崩溃隔离需求、SVG 实测性能瓶颈，而不是文件数量或主观“看起来不够先进”。

## 9. 每阶段门槛

每个结构优化阶段至少满足：

1. 无真实数据、演示数据和凭据删除；
2. OpenAPI、响应 JSON、Hash/URL、SQLite 迁移和 SecretRef 保持兼容；
3. 新增或更新针对性行为测试；
4. 原里程碑验证入口继续通过；
5. 正式部署文档无重复或冲突入口；
6. 事实、待验证风险和实际验收结果记录到 Git 与 Obsidian。
