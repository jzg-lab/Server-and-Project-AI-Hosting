# 目标文档：Project Network Visualization

- **文档状态**：MVP-1 目标、依赖关系与开发顺序已统一
- **版本**：0.6
- **日期**：2026-08-12

## 1. 北极星目标

让用户通过一张可信、可编辑的项目网络图理解和管理已有业务、TechnicalProject、Deployment、HOST 与资源关系：知道服务器上实际观察到了什么，哪些关系由用户确认，能够修正系统归类，并在重新扫描时看见变化。

AI 的近期作用是降低整理成本，不是替代可视化产品本身。原有系统继续运行；本系统首先建立“真实事实 → 可视化草稿 → 用户确认 → 本地投影”的管理闭环。

## 2. MVP-1 成功定义

用户登记一个 Linux HOST 后，不借助命令行即可回答：

1. 这台 HOST 上扫描到了哪些 DeploymentCandidate、服务/容器、网络、卷和项目文档？
2. 它们在当前本地投影中属于哪个项目，彼此是什么关系？
3. 每个节点和关键关系来自哪条事实，是什么时候观察到的？
4. 哪些归类是确定性映射，哪些是 Agent 建议，哪些已由用户确认？
5. 用户能否直接在图或信息岛中修正归类并保存？
6. 再次扫描后，哪些事实新增、变化、消失或与人工投影冲突？
7. 模型不可用时，核心查看与人工管理是否仍然成立？

只完成 SSH 扫描但没有真实图，不算成功；只有 Agent 对话但不能手动管理，也不算成功。

## 3. 当前唯一 MVP-1

当前不再设置互相竞争的“技术 MVP”和“产品 MVP”。MVP-1 同时包含产品价值与必要技术入口：

```text
产品价值：真实数据驱动的可视化管理
技术入口：SSH/Linux 只读发现
辅助能力：基于证据的 Agent 归类与提问
发布边界：单一所有者的互联网访问
```

长期责任网络是 Post-MVP，不影响当前实现排序。

## 4. MVP-1 开发阶段

### M0：冻结视觉基线与数据契约

**目标**：保留现有前端样式和交互，只建立 Fixture 与真实 API 共用的数据边界。

**交付**：

- 固定首批真实页面：全局业务网、项目资源图；
- 固定节点、边、状态、来源、图草稿和页面快照契约；
- 建立 `MockDataSource / HttpDataSource`；
- 用同一份契约运行现有 Fixture，确认画布视觉无回归。

**退出条件**：前端无需改写画布即可在 Mock 与 HTTP 数据源间切换；页面不存在第二套手写业务响应模型。

### M1：取得一个 Linux HOST 的真实事实

**目标**：用最少的后端能力取得可信、可追踪的真实输入。

**交付**：

- Rust/Axum 最小服务、SQLite 迁移和任务状态；
- HOST 登记、SSH 账号密码（默认）或 SSH Key 凭据引用、首次主机指纹确认；
- SSH/Linux 连接基线；按首批 Docker/Compose Provider 检查其只读能力；
- 固定 Docker/Compose 发现和白名单项目文档读取；
- 版本化证据包、来源、时间、哈希、脱敏状态和失败分类。

**退出条件**：一次发现运行能从 API 取回结构化事实；不可达、认证、指纹、权限、Docker、超时和文档失败可以区分。

### M2：真实事实上图并完成人工管理

**目标**：最早证明产品价值，不等待模型、持续监督或复杂 Agent 架构。

**交付**：

- 确定性规则从发现事实生成 DeploymentCandidate 和图草稿；
- HOST、Deployment、服务/容器、网络、卷和文档进入现有画布；
- 节点和关系显示来源、观察时间及 `discovered / draft / confirmed / stale` 状态；
- 用户可以更名、移动、合并、拆分、调整关系、忽略、归档和确认；
- 已确认投影与布局写入 SQLite，刷新后保持一致。

**退出条件**：未配置模型时，用户仍能从一次扫描形成并保存一张可解释的项目图。

### M3：Agent 辅助与重新扫描差异

**目标**：在可用的人工闭环上降低归类成本，而不是替代它。

**交付**：

- URL、Key、Model 的 OpenAI 兼容配置；
- Agent 根据结构化事实和脱敏文档摘要生成带证据引用的建议、问题和补丁；
- 建议预览、采用、拒绝、手动修改和确认；
- 第二次扫描的 `added / changed / missing / conflict / unchanged`；
- 忽略规则和用户确认不会被新扫描静默覆盖。

**退出条件**：Agent 建议可解释且可撤销；模型失败时 M2 闭环保持可用；二次扫描能解释事实与投影差异。

### M4：远程发布门槛

**目标**：把已经成立的产品闭环安全地部署到互联网，而不是在验证价值前先建设完整平台。

**交付**：

- Linux APP_HOST 部署、反向代理和 HTTPS；
- 单一所有者登录、会话保护、限流和审计；
- SSH 密码、SSH Key 与模型 Key 的服务端秘密存储；
- SSE 变化通知、断线快照恢复、用户可重试，以及进程重启后的中断状态恢复；
- 工作区/HOST/项目导出与删除。

**退出条件**：只有所有者能读取业务图和发起扫描；秘密不进入响应、SSE、日志或 Agent 上下文；MVP-1 不修改 TARGET_HOST。

### 阶段关系

```text
M0 视觉/数据契约
  → M1 真实事实
  → M2 可视化管理（首个产品验证点）
  → M3 Agent 辅助与差异
  → M4 远程发布（MVP-1 可发布）
```

M0–M4 全部完成后称为 MVP-1 可发布。M2 完成后即可用真实样本验证方向；如果 M2 的图不解决用户问题，应先修正图与管理流程，而不是继续增加 Agent、权限或基础设施。

## 5. MVP-1 范围

### 必须做

- 保留现有 UI，并把全局业务网、项目资源图接到真实 API；
- 一个 Linux TARGET_HOST 的 SSH 只读接入：默认账号密码，兼容 SSH Key；
- 主机指纹确认、Docker/Compose 与白名单文档发现；
- 确定性图草稿，不依赖模型；
- 人工编辑、确认、布局保存、归档和忽略；
- Agent 归类建议、必要问题和差异补丁；
- 第二次扫描差异、来源和新鲜度；
- Rust/Axum、SQLite WAL、OpenAPI、REST 与 SSE；
- 单一所有者的 HTTPS 远程访问和秘密边界。

### 暂不做

- Docker、服务器、域名、账号或项目文件写操作；
- 暂停、取消、改向、批准等控制动作；
- 多 Agent 协作、责任契约、完整项目脉搏和跨项目协调；
- 多 HOST 编排、多用户、复杂 RBAC、插件市场；
- 流程引擎、图数据库、Redis、独立消息队列和微服务拆分；
- 全盘扫描、完整日志搬运和完整知识库复制；
- 为现有原型的所有页面和按钮同时实现真实行为。

## 6. 首批真实图边界

MVP-1 首批需要真实数据的页面只有：

1. **全局业务网**：业务、已确认项目、待确认的业务关系、状态与真实空状态，不把 HOST 作为业务首屏；
2. **项目资源图**：当前项目的 Compose 服务/容器、网络、卷、端口、文档和关系。

以下内容保留现有视觉但不阻塞 MVP-1：

- 项目流程定义与真实运行轨迹；
- 全局共享组的完整治理；
- 业务统筹 Agent / 项目 Agent 责任状态；
- 外部动作按钮和回执链。

原因是 SSH/Docker 扫描能够证明技术资源关系，但不能凭空证明工作流程、业务承诺或 Agent 责任。先显示能被当前事实支持的内容，避免把样本语义伪装成真实能力。

## 7. 核心指标

| 指标 | 目标方向 |
|---|---|
| 首图时间 | 从 SSH 登记到第一张真实图持续缩短 |
| 映射完整率 | 可识别事实均成为带来源的节点或关系 |
| 人工整理时间 | 用户能快速完成首次更名、归类与确认 |
| 无模型可用率 | 模型不可用时核心闭环通过率为 100% |
| 建议可解释率 | 每项 Agent 建议都有证据引用和理由 |
| 投影稳定性 | 重扫不静默覆盖用户确认和忽略规则 |
| 状态准确性 | `fixture / discovered / draft / confirmed / stale / unavailable` 不混淆 |
| 失败分类完整率 | SSH、Docker、文档、模型和事件流失败均有明确状态 |
| 只读边界 | TARGET_HOST 外部变更次数为零 |
| 秘密泄露 | Key 出现在响应、SSE、日志和模型上下文的次数为零 |

## 8. 每个阶段的完成定义

- 产生一个新的、用户能看见或复核的结果；
- 使用固定输入可以重复验证；
- 失败路径有明确状态和下一步；
- 外部事实、系统映射、Agent 建议和用户决定分开保存；
- 变更有版本、差异和可执行回退；
- 没有因为未来扩展位而提前引入当前不需要的服务或抽象；
- 文档、OpenAPI、前端数据源和实际行为保持一致。

## 9. 关键决策门

### 进入 M1 前

1. 固定首个真实样本 HOST、Docker/Compose 版本和只读权限；
2. 固定证据包与图节点/边最小字段；
3. 固定文档白名单和大小上限。

### 进入 M3 前

4. 用无模型路径验证 M2 确实能形成有用的项目图；
5. 固定哪些冲突必须询问用户，避免 Agent 生成大量低价值问题；
6. 固定模型中转是否需要自定义请求头或路径。

### 进入 M4 前

7. 固定反向代理、HTTPS、登录会话和备份恢复方案；
8. 完成秘密泄露检查与一次数据删除演练；
9. 用第二次扫描验证差异、忽略和人工确认不被覆盖。

## 10. Post-MVP 路线

MVP-1 通过后再按真实使用结果选择：

1. **持续观察**：周期扫描、历史回放、告警与新鲜度策略；
2. **项目 Agent**：项目目标、观察范围、责任契约、异常和项目脉搏；
3. **受控行动**：选择一个可回执、可重读验证、可回滚或可补偿的低影响动作；
4. **跨项目协调**：共享资源冲突、注意力和权限治理；
5. **扩大接入**：第二个 HOST/运行时 Adapter 与多项目复用。

后续顺序必须由 MVP-1 的真实使用瓶颈决定，而不是由愿景文档中对象的数量决定。

## 11. MVP-1 之后的第一条运维纵向切片

下一阶段不直接进入持续控制，而是先把服务器上的部署事实整理成可操作的项目目标：

    SSH/Linux 基线
      → 多 Provider DeploymentCandidate
      → 用户绑定 TechnicalProject / Business
      → ProjectTarget
      → 项目范围 typed read-only Agent

退出条件：

- Docker 缺失时仍能保留 connection_ready，并展示其他 Provider 的覆盖范围；
- 用户可以合并、拆分、绑定和忽略部署候选；
- 一个 TechnicalProject 可以跨多个 HOST 生成多个 ProjectTarget；
- 服务器资产页能分别显示连接、发现、证据新鲜度和待确认关系；
- Project Agent 的每次观察都落到明确的 ProjectTarget；
- 真实持续监控、代码修改和远程控制仍保持独立验收。

### 11.1 下一阶段指标

这些指标只用于“部署发现与项目绑定”阶段，不回写当前 MVP-1 的完成率：

| 指标 | 定义 | 解释边界 |
|---|---|---|
| 候选发现完整率 | 已观察到的部署/运行单元中，成功形成 `DeploymentCandidate` 且带稳定身份与 Evidence 引用的比例 | 分母来自各 Provider 的 `observed_count`；Provider 不可用时同时显示覆盖缺口，不把未知当作未发现 |
| ProjectTarget 绑定率 | 已确认 `Deployment` 中已绑定至少一个有效 `ProjectTarget` 的比例 | 只统计用户确认的部署；未归类候选和被忽略候选不进入分母 |
| 业务确认率 | 已确认 `TechnicalProject` 中已经挂接到 `Business` 的比例 | 业务关系必须由用户确认；跨 Business 复用按关系数记录，不折算成单一归属 |
| Deployment 新鲜度 | 在 freshness policy 窗口内完成最近一次成功观察的活动 `Deployment` 比例 | 连接成功不等于部署新鲜；Provider 失败、过期和未知分别计数 |

指标计算必须保留时间窗口、Provider 覆盖和排除原因，避免把权限不足或未扫描到的对象误判为不存在。

## 12. 终局形态

长期可以形成“可视化项目网络 + 分层 Agent 协作”的系统：真实 Adapter 提供证据，项目 Agent 监督各自项目，业务统筹 Agent 管理注意力与跨项目冲突。但无论终局如何，画布都必须保持事实、来源、用户决定和外部能力边界；长期愿景不得反向扩大当前 MVP-1。
