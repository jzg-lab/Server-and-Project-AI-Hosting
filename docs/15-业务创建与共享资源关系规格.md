# 业务创建与共享资源关系规格

- **状态**：H5、H6 已交付；作为领域边界与后续增强规格持续维护
- **版本**：0.1
- **日期**：2026-08-14
- **适用范围**：Business 创建、TechnicalProject/ProjectTarget 关系、跨 HOST 部署拓扑、共享资源集合与影响反查、Post-MVP 五步路线
- **前置文档**：`00-文档索引.md`、`03-目标文档.md`、`04-MVP决策记录.md`、`05-最小领域模型与权限语义.md`、`08-前后端API与数据架构草案.md`、`10-HOST-SSH初始化与Agent配置规范.md`、`13-运维项目发现与服务器页面规格.md`

> 本文补齐两个此前没有落到可执行规格的问题：用户在哪里创建 Business，以及 `global/resource` 如何基于真实关系展示全部服务器、项目和共享资源。本文不把名称相似、同机部署、同端口或 Agent 猜测当成业务归属。

> **当前实现边界**：旧 `Project`、`Entity`、`ProjectionDraft` 和 `ProjectionVersion` 仍保持可读；H4/H5 已新增稳定目录表、Business 显式项目关系、ResourceEntity 及其 Deployment/TechnicalProject 关系，并提供 `global/resource` 的 topology/shared/impact 只读投影。H6 在此基础上为 TechnicalProject 绑定逻辑 Project Agent，提供固定 typed read-only tools 和调用审计。资源共享只读取这些显式关系，不从名称、同机或旧 `project_id` 推导。

## 1. 先校正五个前提

1. **Business 不能从服务器扫描出来。** 它是用户创建并确认的本地语义分组；扫描器和 Agent 最多提出建议。
2. **HOST 不属于某个 Business。** HOST 是全局基础设施对象。项目通过 ProjectTarget 引用某台 HOST 上的 Deployment，Business 再通过显式关系组织 TechnicalProject。
3. **同机不等于同项目，同名不等于同资源。** 两个部署位于同一 HOST、名称相似或使用同一端口，都不足以建立项目或共享关系。
4. **共享是多条明确引用的结果，不是资源自身的布尔标签。** 同一个稳定资源身份被至少两个不同 TechnicalProject 通过已确认路径引用，才是“已确认共享资源”。
5. **全量展示不等于一次渲染所有低层对象。** 全部 HOST 和项目必须可达且计数完整；Deployment、容器、端口等可以确定性聚合，但必须能展开并说明聚合依据与隐藏数量。

核心不变量：

> 外部观察、确定性路径、用户声明和 Agent 建议是四种不同来源。任何图边都必须能回答“谁建立、依据什么、何时观察或确认、是否仍然新鲜”。

## 2. 最小领域关系

```text
Workspace
├── Business[]
│   └── business_project_links[] ───────┐
├── TechnicalProject[]                  │
│   └── ProjectTarget[]                 │
│       ├── Deployment ── runs_on ── HOST
│       └── adapter / capabilities      │
├── HOST[]                              │
│   └── Deployment[]                    │
└── ResourceEntity[]                    │
    ├── deployment_resource_links[]     │
    └── technical_project_resource_links[]
```

### 2.1 对象职责

| 对象 | 是什么 | 不是什么 | 最小身份 |
|---|---|---|---|
| `Business` | 用户关心的业务结果、跨项目语义分组和策略范围 | 扫描候选、服务器目录、必须拥有独立 Agent 的运行实例 | `business_id` |
| `TechnicalProject` | 一个项目 Agent 的运维责任边界，可跨 HOST | 单个 Compose 名、单个 systemd unit、代码工作区 | `technical_project_id` |
| `ProjectTarget` | TechnicalProject 对具体 Deployment/HOST/adapter 的已确认目标绑定 | 新服务器、外部权限授予、模糊项目归属 | `project_target_id` |
| `Deployment` | 某 HOST 上具有稳定外部身份的部署/运行单元；候选与确认状态共用记录 | Business 或 TechnicalProject | `host_id + provider_kind + external_id` |
| `HOST` | 已登记 Linux 服务器及其连接、身份和 Provider 状态 | 项目的子对象、业务健康 | `host_id` |
| `ResourceEntity` | 网络、卷、镜像、端口、文档、外部存储或入口等稳定资源引用 | 仅凭名称合并的展示标签 | `source + external_id` 或用户声明的本地 ID |

CodeWorkspace 不进入该层级。部署可以保存 `release_id`、`image_digest`、`commit_sha` 等可观察版本元数据，但代码仓库、分支和代码修改继续由专用开发 Agent 管理。

界面中的“服务/部署实例”首版不是第五种领域对象：它是 `Deployment` 的用户可读展示，来源可以是 Compose service、systemd unit、容器组或其他 Provider 的稳定运行单元。Deployment 内更低层的容器、进程和端口按 Evidence/ResourceEntity 展开；只有真实样本证明它们需要独立生命周期和跨 Deployment 身份时，才评估新增 Service 模型，避免 Deployment/Service 双重身份和重复节点。

### 2.2 基数与约束

1. Business 与 TechnicalProject 是 **多对多**。一个业务可包含多个项目；一个共享平台项目也可被多个 Business 显式引用。
2. TechnicalProject 与 ProjectTarget 是一对多。一个跨服务器大项目通过多个 ProjectTarget 表达，不复制多个项目。
3. 一个 ProjectTarget 必须引用一个 TechnicalProject、一个 Deployment 和一个 HOST；`project_target.host_id` 必须等于 `deployment.host_id`。
4. 一个 Deployment 固定属于一个 HOST，但可以被多个 TechnicalProject 通过不同 ProjectTarget 引用，例如共享网关或统一任务 Worker。
5. HOST 只登记一次。项目、Business 和资源视图都引用同一个 `host_id`，不复制服务器记录。
6. ResourceEntity 不保存权威的单值 `project_id`。项目使用关系由明确的关系记录表达；旧 `entities.project_id` 仅作为迁移期兼容字段。
7. 删除 Business 或解除业务—项目关系不删除 TechnicalProject、ProjectTarget、Deployment、HOST 或 Evidence。

### 2.3 关系来源与状态

每条正式关系至少具有：

```text
relation_id
relation_kind
from_ref / to_ref
origin = observed | user_declared | derived
decision_state = observed | linked | confirmed | stale | archived
source_refs[]
path_refs[]              # derived 关系必填
observed_at?             # 外部观察适用
confirmed_by? / confirmed_at?
revision
```

- `observed`：来自 Provider Evidence，例如 Deployment 在某 HOST 上运行、容器挂载卷。
- `user_declared`：用户创建 Business、绑定项目、创建 ProjectTarget 或声明外部共享资源引用。
- `derived`：从已存的明确关系路径计算，例如 `TechnicalProject → ProjectTarget → Deployment → HOST`。它必须保留全部 `path_refs`，不是新的外部事实。
- Agent 结果保持独立的 `proposed` 记录，包含 `reason / confidence / evidence_refs[]`；用户采用后才产生 `user_declared` 关系。`proposed` 不进入默认真实关系计数。

## 3. Business 创建规格

### 3.0 全局页面责任边界

| 导航项 | 首要问题 | 主内容 | 明确不承载 |
|---|---|---|---|
| `global/world` 全局业务网 | 全部 Business 整体怎样 | 粗粒度 Business 看板、业务级状态/覆盖摘要、创建 Business | HOST 资源明细、低层服务拓扑、具体项目投影 |
| `global/resource` 全局资源 | 项目部署在哪里、依赖什么、彼此怎样关联 | HOST—TechnicalProject—Deployment/服务—ResourceEntity 的 topology/shared/impact 关系 | SSH 凭据与重连、HOST 监控主面板、业务大盘 |
| `global/hosts` 服务器 | 每台服务器当前怎样，观测是否可信 | 当前 CPU/内存/磁盘/网络/load/uptime 等状态；连接、采集、发现摘要；下方紧凑健康历史 | Business 创建主流程、空间关系画布、具体项目投影工作台 |
| `scope=project` 项目投影 | 一个具体 TechnicalProject 内部怎样 | 该项目的 ProjectTarget、Deployment、服务、资源、观察和项目 Agent | 全局 HOST 清单、其他业务或其他项目的完整关系 |

四者共享稳定 ID 和深链接，但不复制彼此的主内容。跨页摘要必须能跳到权威页面；摘要不能发展为第二套编辑或关系语义。

### 3.1 唯一主入口

主入口固定在：

```text
#scope=global&view=world
```

页面标题区提供“新建业务”按钮；没有 Business 时，真实空状态提供同一个按钮。候选审查、TechnicalProject 详情或 `global/resource` 中的“挂到业务”只能跳转到同一套全局表单和命令，不形成第二套创建语义。

`global/hosts` 专注服务器状态、连接、监控和发现，不放置“新建业务”主入口，也不因当前 HOST 自动选择候选或项目。`global/resource` 可以按 Business 过滤，并可把当前已确认 TechnicalProject 作为“挂到业务”上下文带回 `global/world`；最终关系仍由用户确认。

### 3.2 最小表单

| 字段 | 必填 | 约束 | 说明 |
|---|---:|---|---|
| `display_name` | 是 | 去除首尾空白后 1–120 个可见字符 | 用户看到的业务名称；不作为稳定身份 |
| `summary` | 否 | 0–500 个字符 | 一句话说明业务结果或边界；不得填凭据 |
| `initial_project_ids[]` | 否 | 只能选择当前 Workspace 中已确认的 TechnicalProject | 便于创建时建立首批显式关系；允许创建空 Business |

`business_id` 由服务端生成，不要求用户填写 slug、颜色、图标、HOST、部署目录、Agent、权限、健康状态或负责人。名称不强制全局唯一；重名时界面提示，但稳定身份始终使用 `business_id`。

### 3.3 命令与结果

建议命令边界：

```text
POST  /api/v1/businesses
PATCH /api/v1/businesses/{business_id}
POST  /api/v1/businesses/{business_id}/project-links
DELETE /api/v1/businesses/{business_id}/project-links/{technical_project_id}
```

创建命令应带 `Idempotency-Key`；修改和解除关系带 `If-Match`。一次创建事务产生：

1. 一条 `Business(state=active, origin=user_declared)`；
2. 零到多条 `business_project_links(state=confirmed)`；
3. 一条不含秘密的审计摘要和变化事件；
4. 新的全局业务读模型修订。

创建 Business 不触发 SSH、发现、部署、项目创建、Agent 会话或外部写操作。新 Business 没有 TechnicalProject 时是合法状态，界面显示“尚未关联项目”，而不是“异常”或“健康”。

### 3.4 绑定 TechnicalProject

- 只允许绑定已存在的 TechnicalProject；DeploymentCandidate 和旧 Project 不能绕过迁移确认直接成为 Business 成员。
- Agent 可推荐候选项目，但“采用建议”仍生成待确认补丁，最终由用户提交。
- 同一 Business—TechnicalProject 活跃关系只能有一条；重复命令按幂等语义返回现有关系。
- 解除关系只归档 link，保留历史修订；项目仍可属于其他 Business，也继续保留全部 ProjectTarget。
- Business 状态和业务健康分开。`active/archived` 是本地生命周期；健康只能由其已确认项目和资源观察聚合，并明确显示覆盖率和更新时间。

## 4. `global/resource` 的真实关系投影

### 4.1 页面职责

路由保持：

```text
#scope=global&view=resource
```

该页面是**全局只读关系投影和影响反查**：所有已登记 HOST、所有已确认 TechnicalProject、迁移期旧 Project、已观察 Deployment 和有明确路径的资源都可从此页到达。它可以显示 HOST 引用和状态摘要，但服务器登记、凭据、重连、扫描按钮仍只在 `global/hosts`。

这一定义细化“共享资源集合与影响反查”：页面不只展示被标记为共享的静态卡片，而是先建立真实拓扑，再从拓扑确定哪些资源被一个或多个项目引用。

### 4.2 读模型

建议使用独立读模型，不复用 `/views/global/world` 的 HOST 兼容节点：

```text
GET /api/v1/views/global/resources
    ?lens=topology|shared|impact
    &focus_kind=host|technical_project|deployment|resource
    &focus_id=<ID>
    &business_id=<ID>
    &technical_project_id=<ID>
    &host_id=<ID>
    &provider_kind=<KIND>
    &state=<STATE>
    &freshness=fresh|stale|unavailable
    &include_candidates=false
```

响应至少包含：

```text
summary               # 全部/当前过滤后的 HOST、项目、部署、共享资源和待确认数
nodes[]
edges[]
facets                # 可用筛选值与计数
coverage[]            # Provider 覆盖与排除原因
hidden_counts         # 聚合、分页、过滤隐藏的数量
meta                  # revision / generated_at / freshness / data_source
```

默认节点集合必须包含所有未删除 HOST 和所有非归档 TechnicalProject，即使它们没有关系边。迁移期非归档旧 Project 以 `legacy_project` 显示并带 `migration_state`，不得伪装成 TechnicalProject。

### 4.3 节点

| 节点 | 默认是否显示 | 身份与状态 |
|---|---:|---|
| `host` | 是 | `host_id`；分别显示 connection、discovery、freshness，不显示虚构业务健康 |
| `technical_project` | 是 | `technical_project_id`；显示关联 Business 数、ProjectTarget 数和覆盖率 |
| `legacy_project` | 迁移期是 | 旧 `project_id`；明确标记“兼容项目，待确认边界” |
| `deployment` | 拓扑展开后 | `deployment_id`；显示 provider、HOST、候选/确认状态、observed_at、coverage |
| `resource` | 有明确关系或成为焦点时 | 稳定 ResourceEntity；显示类型、引用项目数、来源和新鲜度 |

ProjectTarget 默认表现为 `technical_project → deployment` 的目标边及详情卡，不额外绘制大量中间节点；调试或权限详情可以展开 ProjectTarget 记录。这样保留真实对象，又避免为关联表制造视觉噪声。

Business 可以作为筛选条件，并在选中 TechnicalProject 的详情中提供只读归属摘要和跳转 `global/world` 的深链接，但不在 `global/resource` 画布渲染 Business 节点或 Business—项目边。业务关系的权威视觉表达属于 `global/world`。

### 4.4 边

| 图边 | 依据 | 可显示状态 |
|---|---|---|
| `project_targets_deployment` | 已确认 ProjectTarget | user_declared / linked / confirmed / stale |
| `deployment_runs_on_host` | `deployments.host_id` 与 Evidence | observed / confirmed / stale |
| `deployment_uses_resource` | 明确的 mounts/connects_to/exposes/uses_image/documents 等 Evidence | observed / confirmed / stale |
| `project_references_resource` | 用户直接声明的项目—外部资源关系 | user_declared / confirmed / archived |
| `project_impacted_by_host/resource` | 从上述已确认路径生成的影响边 | derived；必须带 `path_refs[]` |

禁止生成以下边：

- 因名称、目录、端口、IP 或标签相似而生成的正式边；
- 因两个项目位于同一 HOST 而生成项目—项目关系；
- 从旧 `entities.project_id` 或中文 facts 单独推断的共享边；
- 从 Agent `confidence` 直接升级的 confirmed 边；
- 将 `connection_ready` 转换成“项目健康”或“业务健康”的边。

### 4.5 共享资源判定

共享范围是读模型结果：

```text
confirmed_project_count(resource) >= 2
```

其中项目必须通过以下任一完整路径到达同一个稳定 ResourceEntity：

```text
TechnicalProject
→ confirmed ProjectTarget
→ Deployment
→ observed/confirmed resource relation

或

TechnicalProject
→ confirmed user-declared project_resource_link
→ ResourceEntity
```

- `confirmed_project_count = 0`：未归类资源；不隐藏，但不叫共享。
- `confirmed_project_count = 1`：项目私有引用。
- `confirmed_project_count >= 2`：已确认共享资源。
- 只有 observed/proposed 路径指向多个项目：显示“可能共享，待确认”，不计入已确认共享数。

同名资源只有在稳定身份相同才合并。两个 HOST 上都叫 `postgres` 的实例默认是两个节点；相反，同一个外部对象存储被三个项目显式引用时只显示一个节点和三条路径。

### 4.6 三种视角

1. **拓扑 `lens=topology`（默认）**：所有 HOST 与 TechnicalProject 作为锚点；以 ProjectTarget/Deployment 展示真实跨服务器关系。
2. **共享集合 `lens=shared`**：只保留已确认共享资源及其项目/HOST 路径；“可能共享”放在单独待确认分组。
3. **影响反查 `lens=impact`**：以选中的 HOST、Deployment 或 ResourceEntity 为中心，展示所有可追溯 TechnicalProject 和下游共享影响。受影响 Business 只在侧栏以跳转摘要列出，不作为资源画布节点。

视角切换只改变投影，不修改关系。URL/Hash 保存 lens、focus 和筛选条件，刷新与前进/后退后保持。

### 4.7 过滤

至少支持：

- Business；
- TechnicalProject；
- HOST；
- Provider；
- 节点/关系状态；
- freshness；
- 已确认共享 / 可能共享 / 私有 / 未归类；
- 是否包含候选和归档对象。

过滤结果同时返回“全部数量、命中数量、因过滤隐藏数量、因 Provider 未覆盖而未知数量”。Provider unavailable 不能被统计为零对象。过滤为空时必须说明是“没有真实关系”还是“当前过滤条件无结果”。

### 4.8 聚合与展开

1. TechnicalProject、HOST 和已确认共享资源的稳定身份节点不互相合并；Business 不进入本画布节点集合。
2. 同一 `TechnicalProject + HOST` 下多个 ProjectTarget 可折叠成一条“`N` 个目标”聚合边；边必须保存全部 `project_target_id` 和 `deployment_id`，点击可展开。
3. 容器、端口、镜像等低层资源可按 Deployment 折叠；聚合节点显示总数、异常数、过期数和隐藏数。
4. 聚合只发生在读模型或前端布局，不写回事实表，不创建新的业务对象。
5. 分页或视图预算导致未渲染时必须返回 `truncated=true` 或 `hidden_counts`，不能让用户误以为对象不存在。

### 4.9 跨服务器大项目

示例：

```text
TechnicalProject: 订单 API
├── ProjectTarget A → Deployment order-api@HOST_A
├── ProjectTarget B → Deployment order-api@HOST_B
└── ProjectTarget C → Deployment order-worker@HOST_C
```

资源图只显示一个“订单 API”项目节点。折叠态分别连接 HOST_A、HOST_B、HOST_C，并标记目标数；展开后显示三个 ProjectTarget/Deployment 路径。任何单台 HOST 的失败只影响对应路径，不把整个项目无依据地标为失败。

### 4.10 多项目引用与共享部署

一个共享网关 Deployment 可以有多个 ProjectTarget：

```text
Project A ── Target A ──┐
                        ├── Gateway Deployment ── HOST_X
Project B ── Target B ──┘
```

Deployment 和 HOST 各显示一次；两个项目的引用分别保留。解除 Target A 不删除 Gateway，也不影响 Target B。共享资源影响通过路径计算，不把 Deployment 的单值 project_id 当作所有权。

### 4.11 空状态与失败状态

| 数据状态 | 页面表达 | 可用入口 |
|---|---|---|
| 无 HOST、无项目 | “尚无服务器或运维项目，暂无真实关系” | 去服务器页登记；去业务页创建 Business |
| 有 HOST、未发现 | 显示孤立 HOST 和“尚未扫描/证据未知” | 去服务器页执行只读发现 |
| 有候选、无项目绑定 | 显示“未归类 Deployment”分组，不造 Project | 进入候选审查 |
| 有 TechnicalProject、无 ProjectTarget | 显示孤立项目和“尚无已确认目标” | 绑定 Deployment |
| 无已确认共享资源 | 共享 lens 显示真实空状态；拓扑仍可用 | 查看可能共享/全部拓扑 |
| Provider 部分失败 | 保留成功路径，并显示 coverage 缺口 | 查看 Provider 详情 |
| 筛选无结果 | 显示当前筛选和被隐藏数量 | 清除筛选 |
| API 不可用 | 显示上次成功修订与 stale/unavailable | 重试；不回退 Fixture |

## 5. 持久化与迁移兼容

### 5.1 建议的增量记录

只增加页面和命令实际需要的结构：

| 记录 | 关键字段 | 说明 |
|---|---|---|
| `businesses` | business_id, workspace_id, display_name, summary, state, revision, created/updated_by/at | 用户创建的业务分组 |
| `technical_projects` | technical_project_id, workspace_id, display_name, summary, state, revision | 正式运维责任边界 |
| `business_project_links` | business_id, technical_project_id, state, confirmed_by/at, revision | 多对多显式关系 |
| `technical_project_legacy_links` | technical_project_id, legacy_project_id, state, confirmed_by/at | 支持旧 Project 的合并、拆分和可逆迁移 |
| `deployments` | deployment_id, host_id, provider_kind, external_id, identity_key, state, freshness, latest_observation_ref | 候选和确认状态共用记录 |
| `project_targets` | project_target_id, technical_project_id, deployment_id, host_id, adapter_kind, capabilities, approval_policy, state, revision | 项目目标绑定 |
| `deployment_resource_links` | deployment_id, resource_entity_id, relation_kind, state, source_refs, observed_at | 外部观察关系 |
| `technical_project_resource_links` | technical_project_id, resource_entity_id, relation_kind, state, confirmed_by/at, revision | 无 Deployment 中间层的显式本地引用 |

不新增 `deployment_candidates` 副本表。候选只是 `deployments.state in (observed, unassigned, linked)` 的读模型。

### 5.2 旧 Project 迁移

现有 `Project` 可能来自 Compose 名、确定性草稿或用户确认，不能批量假定为 TechnicalProject。迁移采用显式映射：

1. 旧 `projects`、`projection_drafts`、`projection_versions` 和原 API 保持可读；迁移不改写历史快照。
2. 全局资源页将旧记录显示为 `legacy_project`，并显示来源与迁移状态。
3. 用户可以把多个旧 Project 合并到一个 TechnicalProject，或把一个旧 Project 拆到多个 TechnicalProject；因此使用多对多 `technical_project_legacy_links`，不只加单值外键。
4. 只有用户确认后才创建 TechnicalProject、business link 和 ProjectTarget。没有足够证据时保留 legacy/unassigned。
5. 旧 `entities.project_id` 在兼容 API 中继续返回；新共享判定只读取明确的新关系。完成迁移前不得双向猜测或静默双写。
6. 回滚只需停用新读模型和新命令；旧表与旧投影仍可读取。新增关系表不得成为旧 HOST/发现 API 的启动前置条件。

### 5.3 API 与图契约兼容

- 新增 `/businesses`、TechnicalProject/ProjectTarget 命令和 `/views/global/resources`；不改变现有 HOST 连接响应。
- `global/resource` 使用独立节点种类，不把 `business` 或 `technical_project` 填进旧 `GraphNodeKind::Project`。
- OpenAPI 和生成类型在同一提交更新；旧客户端可以继续调用旧 world/project resource 端点。
- 新响应必须携带 `schema_version` 或明确契约版本；迁移期间返回 `migration_state` 和 legacy counts。
- 不在前端通过中文 facts、显示名称或节点重复次数重建权威关系。

### 5.4 迁移顺序与门槛

1. **只读影子读模型**：先根据现有明确关系输出 topology，并标记 legacy/unknown；与旧页面并行比较，不写新业务对象。
2. **Business 与 TechnicalProject 本地命令**：增加创建、链接、解除和审计；仍不物化 ProjectTarget。
3. **Deployment/ProjectTarget 物化**：用户确认候选后写稳定记录；旧 ProjectionDraft 继续可读。
4. **共享关系切换**：新 `global/resource` 只依据显式路径判定共享；移除静态资源和中文 facts 推导。
5. **兼容收敛**：当 legacy 项目均已迁移、归档或明确保留后，再评估旧单值 `project_id` 的退场；不得在同一次迁移中删除旧表。

每一步都必须可单独部署、验证和回滚。数据库迁移只追加，不清空现有 HOST、凭据引用、Evidence、用户布局或确认版本。

## 6. 本规格的验收门槛

### 6.1 Business

- 在 `global/world` 可只填名称创建空 Business；刷新后仍存在，且没有自动生成项目、HOST 或健康边。
- 可把已确认 TechnicalProject 绑定到一个或多个 Business；解除一个关系不删除项目和其他关系。
- 同名 Business 使用不同 ID；重复 Idempotency-Key 不产生副本。
- Agent 建议在用户确认前不进入 Business 项目计数。

### 6.2 关系真实性

- 一个 TechnicalProject 跨三个 HOST 时只显示一个项目节点和三个可展开目标路径。
- 两个项目引用同一稳定 ResourceEntity 时资源节点只出现一次；两项同名但 identity 不同的资源保持两个节点。
- 同一 HOST 承载多个项目时不自动生成项目—项目关系或 Business 归属。
- 每条 observed/user_declared/derived 边分别携带 source_refs、确认信息或 path_refs；任一引用可跳转到证据/决定详情。
- Provider unavailable 显示 coverage unknown，不把未知对象计为零。

### 6.3 页面与兼容

- topology、shared、impact 三个 lens 的 URL 状态可刷新恢复；过滤前后计数与隐藏数一致。
- 所有登记 HOST 和非归档 TechnicalProject 可达；孤立节点有明确空状态。
- `global/resource` 不出现凭据、SSH 编辑、重连或发现控件；这些入口跳转 `global/hosts`。
- HTTP API 不可用时不展示静态 Fixture 为真实数据。
- 旧 Project、ProjectDraft、project resource API 与历史投影仍可读取；新模型不静默改写它们。

## 7. 既定 Post-MVP 五步的依赖审计

`docs/03` 已列出五个未来方向：持续观察、项目 Agent、受控行动、跨项目协调、扩大接入。它们不是五个可并行堆叠的页面按钮，必须按领域与证据依赖拆分。

| 方向 | 必要依赖 | 迁移/兼容 | 验收门槛 | 主要成本与风险 |
|---|---|---|---|---|
| **持续观察** | HOST 资源观察只依赖稳定 HOST、SSH 只读采集、freshness policy、并发与保留策略；Deployment/Target 健康另需稳定 Deployment、ProjectTarget 与期望状态 | 新增调度/心跳记录；保留手动扫描与现有 DiscoveryRun；旧运行不补造心跳 | HOST 层至少完成连续多轮资源采样；Target 层在绑定完成后再验收；不会同 HOST 重入；错过、超时、部分成功和停用可区分；保留与压缩可验证 | SSH/CPU/网络负载、SQLite 增长、告警噪声、时钟与离线恢复 |
| **项目 Agent** | TechnicalProject、ProjectTarget、固定 typed read-only tools、足够新鲜的观察 | H6 新增逻辑绑定和调用审计；现有 onboarding Agent 继续用于候选建议；不把旧模型配置自动升级为责任契约 | 每次目标工具调用显式 project_target_id；跨项目读取被阻断；无任意 Shell；结果引用观察时间和 Evidence；模型失败不影响图 | 模型费用、上下文膨胀、幻觉、跨项目数据泄漏、长期记忆漂移 |
| **受控行动** | 稳定 ProjectTarget、专用 adapter、能力/审批、幂等回执、基线、重读验证、回滚/补偿 | read_only 能力永不自动升级；新增 ActionRequest/Receipt；默认关闭；旧按钮保持不可执行 | 先只验收一个低影响动作；成功必须有外部回执和重读一致；失败、超时、重复请求和回滚均有实测 | 生产中断、权限扩大、不可逆副作用、秘密处理、供应商差异；风险最高 |
| **跨项目协调** | Business、business_project_links、真实共享资源图、ProjectTarget、项目摘要/脉搏、跨项目读取策略 | 不从名称或共享 HOST 自动创建 Business；旧全局 world 保留到新业务读模型验收；建议与确认分层 | 共享资源影响不漏不重；Business/项目关系均可追溯；一个项目可服务多个 Business；权限与私有数据边界可验证 | 关系组合爆炸、错误所有权、画布过载、跨项目隐私、协调建议误导 |
| **扩大接入** | 明确的真实样本与覆盖缺口、固定只读 Provider 合约、稳定 external_id、限额和脱敏规则 | Provider 增量注册；旧 Docker/Compose/systemd 行为与状态保持；unsupported/unavailable 明确 | 每个新 Provider 有真实样本、成功空结果、权限不足、超时、脱敏、限额和部分成功测试；不降低 connection_ready | 运行时矩阵、版本差异、远端权限、命令输出漂移、维护与支持成本 |

### 7.1 建议顺序

HOST 资源监控和项目/业务关系是两条依赖不同的路线：HOST 级资源快照、调度和历史只依赖已登记 HOST，不需要等待 TechnicalProject；Deployment、ProjectTarget、项目健康和业务汇总则必须等待领域关系稳定。默认顺序因此拆为：

```text
0A. 已完成：同步当前运行版本，并让 hosts 读模型脱离 global/world 的 HOST 兼容节点
→ 0B. HOST 级一次性资源快照 → 周期调度 → 健康时间带与保留
→ 0C. Business / TechnicalProject / Deployment / ProjectTarget 与真实 global/resource
→ 0D. 已完成：TechnicalProject 绑定的 typed read-only Project Agent
→ 5. 扩大接入（只补当前真实样本阻塞的一个 Provider）
→ 1. Deployment / ProjectTarget typed 持续观察
→ 2. 项目 Agent 的责任契约、周期托管和项目脉搏
→ 4. 跨项目协调
→ 3. 受控行动
```

理由：

1. HOST 级 CPU、内存、磁盘和网络观察可先独立落地；没有稳定对象和明确关系时，只后置 Target/项目健康、业务汇总和项目 Agent，不用缺失的领域模型阻塞主机监控。
2. 扩大接入先做“最小缺口”，优先用户确认根目录/documents；若现有 Docker/Compose/systemd 已足够完成真实绑定，可跳过该增量直接进入持续观察。
3. Project Agent 需要稳定目标和有时效的观察，因此晚于 ProjectTarget 和持续观察。
4. Business 创建与共享资源读模型现在就落地，但“跨项目协调 Agent/策略”要等项目级事实与权限成熟；两者不可混称。
5. 受控行动有最高外部风险，最后进入，并且只从一个可验证、可回滚的动作开始。

### 7.2 非固定瀑布的决策门

- 用户因缺少事实无法绑定 Deployment：只增加对应 Provider，不建设通用插件平台。
- 已能稳定绑定但证据频繁过期：优先持续观察，不继续增加 Provider 数量。
- 项目边界和 ProjectTarget 尚不稳定：暂停项目 Agent，不用提示词掩盖模型缺口。
- 共享影响路径尚不能完整解释：暂停跨项目协调，不生成全局风险结论。
- 任何动作缺少外部回执、重读验证或回滚：保持 read_only，不开放控制入口。

## 8. 明确后置

- Business Agent 实例、多 Agent 委托网络和复杂 RBAC；
- 任意 SSH Shell、自动提权和全能远程控制；
- 根据名称或模型推理自动确认 Business/TechnicalProject；
- CodeWorkspace、分支、代码修改与开发 Agent；
- 图数据库、通用插件市场和通用工作流引擎；
- 在没有调度、历史和告警机制时把“最近一次观测”称为持续监控。

本文的首要交付价值是：用户可以先明确创建 Business，再用可追溯关系把跨 HOST 的 TechnicalProject、Deployment 和共享资源组合起来；Agent 和控制能力只能建立在这套已确认关系之上。
