# 产品需求文档（PRD）

- **文档状态**：当前 MVP-1 范围与开发优先级已统一
- **版本**：0.8
- **日期**：2026-08-12
- **项目**：Project Network Visualization

## 1. 产品摘要

Project Network Visualization 是一个从**可视化管理**入手的项目网络工具。它把已有服务器中的项目、服务、容器、网络、卷、文档及其关系转换成可探索的图，让用户能够看清现状、整理归属、修改本地投影、确认结果并追踪后续变化。

系统不替代 Docker、服务器或既有项目，也不在首版承担外部控制。原系统提供事实，本系统保存可解释的本地投影。

### 1.1 当前产品 MVP-1：真实数据可视化管理闭环

MVP-1 只验证一件事：

> 用户登记一个 Linux HOST 后，能够在现有画布中看到由真实 Docker/Compose 和项目文档生成的项目网络，并能手动整理、确认、保存和重新扫描比较。

完整闭环为：

```text
登记 Linux HOST
→ SSH 账号密码（推荐）或 SSH 私钥 + 首次主机指纹确认
→ 固定只读扫描 Docker/Compose 与白名单项目文档
→ 确定性规则生成可编辑图草稿
→ 用户查看和整理
→ Agent 可选地提出归类建议、关系解释和问题
→ 用户确认
→ 发布本地投影
→ 再次扫描并显示差异
```

### 1.2 核心依赖规则：图先于 Agent

扫描器产生事实，确定性映射器把事实转换成节点、关系和初始分组，Agent 只增强草稿。以下路径必须始终成立：

```text
未配置模型 / 模型调用失败
→ 扫描结果仍可见
→ 图草稿仍可编辑
→ 用户仍可确认并保存投影
```

这不是降低 Agent 的价值，而是避免把模型可用性变成可视化管理的单点故障。Agent 输出只能进入 `proposal` 或 `projection_draft`，不能直接成为已确认事实。

### 1.3 Post-MVP 愿景

持续观察、每项目 Agent、责任契约、项目脉搏、跨项目协调、共享知识治理和外部受控行动属于后续方向，详见 `docs/11`。这些对象不进入 MVP-1 的数据库必建表、API 必做项或验收条件。

### 一句话价值

> 先把服务器中真实存在的项目和资源变成一张可管理的图，再让 Agent 帮用户整理，而不是先建设一套复杂的 Agent 管理体系。

## 2. 用户问题

当前最需要解决的不是“AI 能否自动托管项目”，而是更基础的可见性问题：

- 一台服务器上有哪些项目、Compose 服务和容器，归属不清楚；
- 项目、网络、卷、端口和文档之间的关系分散在命令输出与文件中；
- 现有前端原型有完整视觉表达，但数据仍主要来自 Fixture，不能反映真实环境；
- 自动扫描可能误归类，用户需要在图上修正而不是修改底层数据文件；
- 再次扫描时，难以看出新增、消失、变化、人工确认和忽略之间的差异；
- 项目文档能补充语义，但纯规则不能理解所有命名，纯模型又可能产生未经核验的推断。

## 3. 产品目标与优先级

### P0：MVP-1 发布阻塞项

1. **真实数据上图**：一个 Linux HOST 的 Docker/Compose 和白名单文档能够进入草稿与项目资源图；HOST 自身在服务器资产页管理，不填充业务首屏。
2. **人工可管理**：用户能查看来源，并执行更名、移动、合并、拆分、忽略、确认和保存。
3. **事实可追踪**：每个节点和关键关系能说明来源、观察时间和当前状态。
4. **重新扫描可比较**：新扫描不会静默覆盖人工确认；新增、变化、消失和冲突可见。
5. **真实前后端连接**：生产页面通过 Rust API 读取和修改投影，不直接依赖页面全局 Fixture。
6. **安全远程部署**：系统能部署在 Linux APP_HOST，经 HTTPS 由单一所有者访问，SSH 密码、私钥和模型 Key 不返回浏览器。
7. **只读目标边界**：MVP-1 不修改 TARGET_HOST、Docker 或项目文件。

### P1：MVP-1 内的增强项

8. **Agent 辅助初始化**：读取结构化事实和脱敏文档摘要，提出可解释、可编辑的归类建议和问题。
9. **进度与变化通知**：长任务状态和投影变化通过 SSE 通知，断线后以快照恢复。

P1 仍属于 MVP-1 计划，但实现顺序在真实图与人工管理之后；P1 失败不得破坏 P0 闭环。

### Post-MVP

- 周期性无人值守监督、完整历史回放和复杂告警；
- 业务统筹 Agent 与每项目 Agent 的责任网络；
- `ProjectCharter`、`ResponsibilityContract`、完整 `ProjectPulse`；
- 流程执行、外部暂停/取消/改向/批准等控制动作；
- 多 HOST 编排、多用户组织、复杂 RBAC 和共享知识治理；
- 第二种运行时、插件市场、图数据库和通用工作流引擎。

## 4. 产品边界

### 4.1 MVP-1 包含

- 登记一个 Linux TARGET_HOST，并保存地址、端口、SSH 用户、凭据引用和指纹状态；
- 默认使用 SSH 账号密码，也支持用户明确提供的 SSH 私钥；首版账号密码登录支持标准 SSH Password Authentication 与常见的单密码 Keyboard-Interactive/PAM。系统不扫描本机或 APP_HOST 的私钥集合，不盲试多把私钥；多因素/MFA、多轮交互、SSH Agent 和“密码登录后安装托管公钥”后置。首次指纹由服务端取得并在界面中交给用户确认；
- 执行固定只读 Docker/Compose 发现和受限项目文档读取；
- 保存结构化事实、来源、时间、哈希、脱敏状态和失败原因；
- 用确定性规则生成初始项目、实体、关系和图草稿；
- 在全局业务网和项目资源图中显示真实节点、关系、状态与来源；
- 支持手动更名、移动、合并、拆分、忽略、归档和确认；
- 配置一个 OpenAI Chat Completions 兼容模型服务的 URL、Key、Model；
- Agent 根据证据提出建议、解释和问题，用户决定是否采用；
- 保存已确认投影、布局、用户决定和最小审计；
- 重新扫描并显示事实变化与投影差异；
- 通过 REST 快照/命令和 SSE 连接现有前端；
- 提供单一所有者登录、HTTPS 部署边界、导出和删除入口。

### 4.2 MVP-1 排除

- 任意 SSH 命令、自动 `sudo`、目标机常驻程序；
- 修改或删除容器、镜像、网络、卷、项目文件和服务器配置；
- 暂停、取消、改向、批准或其他外部控制动作；
- 把 Agent 建议自动发布为事实；
- 全盘扫描、读取所有环境变量、复制完整日志或完整知识库；
- 把技术资源正常推断为完整业务项目健康；
- 为现有前端原型中的流程、控制、共享治理和全部按钮同时建设真实后端；
- 多 Agent 基础设施、复杂责任语义和跨项目自动协调。

### 4.3 现有 UI 与真实能力的关系

现有 UI 的布局、画布、信息岛、拖拽反馈、运行/编辑视觉和历史轨迹是设计基线，继续保留。保留视觉不等于 MVP-1 必须实现其背后的全部运行能力：

- MVP-1 首批真实数据页面是**全局业务网**和**项目资源图**；
- 项目流程、运行回执、全局共享治理和控制按钮可以保留样本或禁用状态；
- 界面必须区分 `fixture`、`discovered`、`draft`、`confirmed`、`stale` 和 `unavailable`，不得把样本显示成真实状态。

## 5. 目标用户与典型场景

### 5.1 目标用户

首版面向在一台或少量 Linux 服务器上运行多个 Docker/Compose 项目的单一所有者，希望通过互联网打开一个统一界面查看和整理项目关系。

### 5.2 典型任务

> 用户登录应用，登记一个 Linux HOST 和 SSH 账号密码（也可选择 SSH 私钥），确认服务端展示的主机指纹。系统通过可用 Provider 只读发现部署和资源，立即在现有画布中显示候选草稿。若配置了模型，Agent 再依据证据解释归类并询问缺失信息。用户直接修改或采用建议，确认后发布本地投影；再次扫描时看到新增、变化、消失和冲突。

## 6. 核心概念

| 概念 | 当前含义 |
|---|---|
| 工作区 | 远程部署实例的单一所有者边界 |
| HOST | 通过 SSH 登记并被只读发现的 Linux 主机 |
| 发现运行 | 一次有开始、进度、结果、错误和结束状态的扫描任务 |
| 发现事实 | Docker、Compose、文件和文档中直接读取到的结构化证据 |
| 图草稿 | 由确定性规则从事实生成、尚未由用户确认的节点与关系集合 |
| Business | 用户关心的业务结果，可跨多个 TechnicalProject 和 HOST |
| TechnicalProject | 一个 Project Agent 的运维责任范围，可跨多个 HOST |
| DeploymentCandidate | Provider 依据 Evidence 归并出的部署候选，不是正式项目 |
| Deployment | 用户确认后的稳定部署实例，例如 Compose、systemd 或 PM2 单元 |
| ProjectTarget | TechnicalProject 与具体 Deployment/HOST 的本地目标绑定 |
| 项目 | 用户确认后的本地技术项目投影；不代表外部项目被创建 |
| 实体 | HOST、Compose 项目、服务、容器、镜像、网络、卷、端口和文档等对象引用 |
| 关系 | `contains`、`deploys`、`connects_to`、`mounts`、`depends_on`、`documents` 等有来源的边 |
| Agent 建议 | 基于事实和文档的归类、关系解释、问题或投影补丁，不是事实 |
| 本地投影 | 用户确认后的项目、实体、关系、布局和忽略规则 |
| 来源/新鲜度 | 事实来自哪里、何时观察、当前是否过期 |
| 模型服务 | OpenAI 兼容的 URL、Key 引用和 Model 配置 |
| 凭据引用 | 服务端秘密存储中的 SSH 密码、SSH Key 或模型 Key 引用，不包含秘密正文 |

## 7. 核心用户流程

### 7.1 第一条可见纵向切片

1. 前端通过 `HttpDataSource` 取得 `bootstrap` 和空的真实图读模型。
2. 用户登记 HOST、SSH 用户和 SSH 账号密码或 SSH Key 引用。
3. 服务端取得新主机指纹；用户确认后执行 SSH/Linux 基线检查。
4. 系统按可用 Provider 启动一次只读发现，前端显示各 Provider 状态和明确错误。
5. 发现完成后，确定性映射器生成 DeploymentCandidate 和图草稿。
6. 前端显示 HOST、部署候选、服务/容器、网络、卷、文档节点及关系。
7. 用户能在不配置模型的情况下修改并确认投影。

完成第 7 步即证明“真实数据 → 可视化管理”的核心价值，后续功能不得延迟这条切片。

### 7.2 完整 MVP-1 闭环

8. 用户配置可选的模型 URL、Key 和 Model。
9. Agent 读取结构化事实、脱敏文档摘要和当前草稿，提出建议和少量必要问题。
10. 用户可采用、拒绝或编辑建议；应用前显示差异。
11. 用户确认后发布投影，保存布局、决定与证据引用。
12. 用户再次扫描；系统并列显示新事实、旧投影和差异，不静默重分类。
13. 归档或忽略规则继续生效；用户可手动恢复。

### 7.3 失败与降级

- SSH、指纹或 Linux 基线失败：停止该轮发现，显示具体阶段和重试入口；单个 Provider 失败只降低发现覆盖范围，并保留其他 Provider 的结果。
- 项目文档读取失败：Docker 事实仍可上图，文档节点标记失败或缺失。
- 模型未配置或调用失败：保留图草稿和人工编辑路径，Agent 区域显示不可用原因。
- SSE 断线：前端重新请求任务和图快照；最终状态不依赖事件是否送达。
- 重新扫描发现冲突：生成差异和待确认项，不覆盖已确认投影。

## 8. 功能需求

### FR-001 真实数据源边界

现有前端应通过统一 `DataSource` 读取数据；Fixture 与 HTTP 使用同一节点、边、状态和页面读模型契约。生产默认使用 `HttpDataSource`，页面不得散落直接请求或重复全局 Fixture。

### FR-002 HOST 登记与 SSH 连接

系统应登记 Linux HOST、地址、端口、SSH 用户、凭据引用和主机指纹状态。MVP-1 默认支持 SSH 账号密码并兼容用户明确提供的 SSH Key；主机指纹确认、连接检查、超时和失败原因必须可见。账号密码是首次接入和认证失败补救的兜底入口，不得因找不到私钥而阻断登录。

### FR-003 部署 Provider 与文档发现

MVP-1 已实现 Docker/Compose 与白名单文档发现。下一阶段按 Provider 发现 Compose stack/service、systemd unit、PM2 app、受限进程组和端口绑定，并从用户确认的目录读取清单/文档元数据。每个 Provider 独立返回 ready、unavailable、permission_denied、timed_out 或 failed；文件数量、大小和路径范围受限。

### FR-004 确定性图草稿

系统应在不调用模型的情况下，把发现事实归并为带稳定外部身份的 DeploymentCandidate，并转换成可查看的图草稿。用户确认后才生成 Deployment 和 ProjectTarget；每个节点和关键关系包含稳定身份、类型、来源引用、观察时间和草稿状态；不确定归属保持 `unassigned`，不由规则猜测。

### FR-005 可视化管理与投影发布

用户应能在图或信息岛中命名 TechnicalProject、绑定或解除 ProjectTarget、合并/拆分部署候选、修改本地关系、忽略对象、归档投影和保存布局。所有修改先进入草稿，确认后才成为当前本地投影，并保留版本与撤销依据。

### FR-006 Agent 辅助初始化

Agent 应只接收结构化事实、脱敏文档摘要、已确认规则和当前草稿；输出带证据引用的建议、问题、理由、置信度和可编辑补丁。模型不可用不得阻止 FR-004 与 FR-005。

### FR-007 重新扫描与差异

重新扫描应产生新的事实快照，并显示 `added / changed / missing / conflict / unchanged`。用户确认过的归类和忽略规则不会被静默覆盖；外部对象消失与用户删除投影是不同状态。

### FR-008 进度与 SSE

发现进度、Agent 建议和投影变化通过 SSE 通知；事件只表示“哪里变化”，前端随后重新读取快照。断线、游标过期或漏事件时，以 REST 最终状态为准。

### FR-009 模型服务配置

用户只需配置 OpenAI Chat Completions 兼容的 URL、Key 和 Model。首版非流式，不要求模型列表接口、自定义 Agent 平台或复杂 Provider 抽象；Key 只保存为服务端秘密引用。

### FR-010 远程发布

系统部署在 Linux APP_HOST，通过 HTTPS 互联网访问。发布版必须有单一所有者登录、会话保护、限流、审计、严格来源设置和秘密边界；开发阶段可先在受限环境完成纵向切片，但这些是公开发布门槛。

### FR-011 数据保留与删除

默认保留当前投影、用户决定、忽略规则和审计摘要直到用户删除；每个 HOST 保留最近 3 次完整脱敏扫描，更早记录只保留摘要、哈希、时间和差异；原始 SSH 输出、完整文档正文和完整模型输入输出不进入长期库，任务临时数据最多保留 24 小时。提供按工作区/HOST/项目删除和导出能力。

### FR-012 下一阶段运维资产与目标绑定

下一阶段应在保持 MVP-1 只读边界的前提下：

- 由 Docker/Compose、systemd、PM2、端口/进程和用户确认目录 Provider 产生 DeploymentCandidate；
- 允许用户将候选合并、拆分、绑定到 TechnicalProject 或 Business，或保持未归类；
- 在用户确认项目边界后生成 ProjectTarget，明确 HOST、Deployment、适配器和只读能力；
- 提供 global/hosts 服务器资产与最近观测页面，分别展示连接状态、发现状态、Provider 覆盖和证据新鲜度；
- Project Agent 只通过项目范围内的 typed read-only tool 读取 ProjectTarget，持续监控、远程写入和代码操作另行设计。

## 9. MVP-1 开发顺序与验收

### M0 视觉契约与真实数据源

- 冻结现有 UI 的主要布局和交互；
- 固定节点、边、状态、来源和图草稿契约；
- 建立 `MockDataSource / HttpDataSource`，同一页面可切换固定样本与真实 API。

### M1 SSH 事实链

- 登记一个 Linux HOST；
- 通过 SSH 账号密码或 SSH Key 和用户确认的主机指纹完成连接检查；
- 完成一次 Docker/Compose 与白名单文档只读发现；
- 错误能区分不可达、认证、指纹、权限、Docker、超时和文档读取失败。

### M2 可视化管理闭环（最先证明用户价值）

- 发现事实无需模型即可生成图草稿；
- 全局业务网和项目资源图显示真实项目、资源、关系、来源和时间；
- 用户可修改、确认和保存投影；刷新页面后状态一致；
- 生产页面的这两类数据不再来自全局 Fixture。

### M3 Agent 辅助与重新扫描

- URL、Key、Model 配置可用；
- Agent 生成至少一条带证据的建议和一个必要问题；
- 用户可采用、拒绝或编辑，模型失败时人工路径仍通过；
- 第二次扫描显示差异，已确认投影与忽略规则不被静默覆盖。

### M4 远程发布门槛

- Rust 服务在 Linux APP_HOST 启动，经 HTTPS 访问；
- 只有所有者会话能登记 HOST、读取业务图和修改投影；
- SSE 断线后可恢复最终状态；
- SSH 密码、SSH Key、模型 Key、完整文档和原始输出不出现在 API、SSE、日志与 Agent 回复；
- 整条 MVP-1 路径不修改 TARGET_HOST，也没有可执行的外部控制按钮。

M0–M4 全部满足后才称为 MVP-1 可发布；开发时严格按 M0 → M1 → M2 → M3 → M4 推进。M2 是最早的产品验证点，不等待 M3/M4 才进行用户试用与方向判断。

## 10. 非功能需求

- **可解释**：事实、确定性映射、Agent 建议和用户决定分别标记；
- **可恢复**：异步任务和草稿写入数据库，不依赖浏览器单次会话；
- **可追踪**：节点、关系、建议和投影变更有稳定 ID、来源与版本；
- **最小基础设施**：Rust/Axum 模块化单体、SQLite WAL、任务内临时载荷和服务端受限权限秘密文件；
- **契约一致**：OpenAPI 从 Rust 路由与 DTO 生成前端类型，不维护第二套手写响应类型；
- **性能基线**：目标样本规模下，图快照与编辑保持流畅；达到实测瓶颈前不引入图数据库、Redis 或消息队列；
- **数据最小化**：不长期保存完成当前图解释所不需要的原始内容。

## 11. 成功指标

- 从完成 SSH 登记到出现第一张真实图的时间；
- 扫描事实成功映射为带来源节点/关系的比例；
- 用户完成首次项目整理和确认所需时间；
- 模型不可用时仍能完成核心闭环的比例应为 100%；
- Agent 建议被采用、修改、拒绝及其耗时；
- 第二次扫描正确保持用户确认和忽略规则的比例；
- 外部事实与 Agent 推断混淆次数为零；
- 目标 HOST 被 MVP-1 修改的次数为零；
- SSH 密码、SSH Key 或模型 Key 出现在响应、事件和日志中的次数为零。

## 12. 已锁定项与待决策问题

### 已锁定

- MVP-1 的产品主语是可视化管理，不是多 Agent 托管；
- 一个 Linux TARGET_HOST，SSH 是核心入口，默认使用账号密码、兼容用户明确提供的 SSH Key；账号密码登录覆盖标准 Password Authentication 与单密码 Keyboard-Interactive/PAM；系统不自动发现或盲试私钥；多因素/MFA、多轮交互、SSH Agent 和托管公钥安装后置；
- 首次主机指纹由服务端取得并在界面中由用户确认；
- 模型只配置 URL、Key、Model，采用 OpenAI Chat Completions 兼容非流式请求；
- 控制动作后置；
- 系统部署在 Linux APP_HOST，经互联网访问；
- Agent 不阻塞确定性上图和人工管理。

### 实现前仍需从样本确认

1. 目标 HOST 的 Docker/Compose 版本、rootless 模式与实际只读权限；
2. APP_HOST 与 TARGET_HOST 是否为同一台机器；即使同机，也按显式 TARGET_HOST 登记；
3. 文档白名单、单文件上限、总文件数和总大小；
4. 反向代理、域名、HTTPS 和所有者登录方案；
5. 模型中转是否需要自定义请求头或路径；默认不需要；
6. 首个真实样本图的规模，用于确定布局与快照性能基线。
