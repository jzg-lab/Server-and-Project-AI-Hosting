## 1. 先校正六个前提

1. **连接不等于健康。** `connection_ready` 只表示网络可达、SSH 已认证并能读取 Linux 身份。CPU、内存、磁盘或服务异常不得反写成 SSH 认证失败。
2. **发现不等于监控。** Docker/Compose/systemd 发现回答“观察到哪些运行单元”；资源采样回答“某段时间资源怎样变化”。二者有不同周期、保留和失败语义。
3. **最近一次正常不等于持续正常。** 每几小时采一次只能证明采样点附近可观察；两个采样点之间的短故障、尖峰和抖动仍然未知。
4. **主机资源正常不等于项目或业务正常。** HOST 资源条件、Deployment 状态、Project Agent 周期和 Business 健康必须分轴显示。
5. **监控界面不等于监控系统。** 页面能显示“最近观测”并不代表已有调度、历史、降采样、阈值、告警和恢复语义。
6. **采集越密并非越好。** 更短周期提高可见性，同时线性增加 SSH、SQLite、备份和页面查询成本；周期必须服从实际故障持续时间和成本预算。

核心不变量：

> 采集成功只证明取得了数据；数据新鲜只证明时间上仍有效；阈值评价只覆盖已配置、已观察的维度；未知永远不能折算成正常。

## 2. 事实、参考和建议的分层

### 2.1 当前仓库的实现事实

- 正式拓扑是 Linux APP_HOST 上的 Rust/Axum 模块化单体、SQLite、FileSecretStore 和 OpenSSH；TARGET_HOST 保持只读访问。
- 当前已有人工连接检查、Docker/Compose/systemd 发现、手动资源快照、持久化 interval 调度、typed raw 主机指标时序、UTC hour/day rollup、周期 compactor 与维护状态；仍没有版本化健康策略、健康时间带或告警领域。
- `GET /api/v1/views/global/hosts` 已分开展示连接、最近发现、Provider coverage 和兼容推导的新鲜度。
- 当前 `Freshness` 主要由发现状态与 Evidence 保留层级推导，不是以 `observed_at + stale_after` 计算的监控时间窗口。
- `/healthz` 只验证 Network Atlas 进程与 SQLite；SSE 每 15 秒的 comment heartbeat 只用于连接保活。二者都不是 TARGET_HOST 心跳。
- Docker 容器 healthcheck 和 systemd `active/sub` 目前只是 Evidence/图节点事实。只有绑定稳定 Deployment/ProjectTarget 并声明期望状态后，才可进入目标健康评价。
- 当前 discovery 与 monitor 通过 SQLite 共同保证每个 HOST 只有一个活动观察任务；H2 调度采用持久化 due time、领取租约和最多一次 catch-up，重启将遗留 run 标为 `interrupted`，不会洪泛补跑。

### 2.2 外部文章能支持的事实

参考文章：[黑炫酷的监控界面，实际上是用了什么开源工具？](https://zhuanlan.zhihu.com/p/480604859)（2022-03-14，入门教程）展示了常见组合：

```text
Prometheus Server 拉取指标
├── node_exporter：服务器指标
├── cAdvisor：容器指标
├── 应用暴露的指标端点
├── Grafana：查询与可视化
└── Alertmanager：告警分发
```

文章还指出，抓取间隔和界面查询间隔决定可见粒度：按 N 秒拉取只能描述离散采样与时间段趋势，难以复原未被采到的瞬时值。

这篇文章是架构启发，不是本项目阈值或部署方式的权威来源。它通过 Docker 安装并在目标环境暴露 exporter 端口；这会修改目标机并增加常驻组件、端口、升级和凭据成本，超出当前 TARGET_HOST 的 SSH 只读边界。

Linux 指标字段与限制以一手资料为准：[/proc 文件系统](https://docs.kernel.org/filesystems/proc.html)、[块设备 I/O 统计](https://docs.kernel.org/admin-guide/iostats.html)、[网络接口统计](https://docs.kernel.org/networking/statistics.html)、[hwmon sysfs ABI](https://docs.kernel.org/hwmon/sysfs-interface.html) 和 [`proc_meminfo(5)`](https://man7.org/linux/man-pages/man5/proc_meminfo.5.html)。

### 2.3 本文的工程建议

同时保留两条接入路径，但不一次实现两套基础设施：

1. **首条路径：agentless SSH 周期快照。** 复用现有严格主机指纹、SecretRef、固定只读动作和输出上限，先验证指标语义、页面和成本。
2. **后续路径：读取用户已有的 Prometheus。** 只有真实环境已经部署并愿意提供只读入口时，增加受控 Adapter；不由 Network Atlas 默认安装 node_exporter/cAdvisor/Prometheus，也不要求 Docker 存在。

Prometheus 路径适合秒级到分钟级趋势和较多 HOST；SSH 快照适合少量 HOST、分钟级概览和无需安装组件的起步阶段。两条路径必须归一化为相同的 Observation/Condition 契约，页面不因来源不同改变健康语义。

## 3. 状态必须正交

| 状态轴 | 建议值 | 回答的问题 |
|---|---|---|
| APP probe | `ok / unavailable` | Network Atlas 进程与 SQLite 是否可用；沿用 `/healthz` |
| Scheduler | `running / late / stopped / unknown` | APP 内监控调度循环是否按计划工作 |
| HOST connection | `unknown / checking / connection_ready / failed / host_key_unverified / host_key_changed` | APP_HOST 是否能通过 SSH 读取 Linux 身份 |
| Monitor run | `queued / running / succeeded / partial / failed / timed_out / skipped_overlap / interrupted` | 本次固定资源采集是否执行完成 |
| Metric quality | `observed / insufficient_interval / counter_reset / counter_unreliable / unsupported / permission_denied / timed_out / parse_failed` | 单项指标是否可用于计算 |
| Observation freshness | `fresh / stale / unknown` | 最近有效观察是否仍在时间窗口内 |
| Resource condition | `ok / warning / critical / unknown / stale` | 已配置阈值下，某个资源维度结果怎样 |
| Discovery | `discovery_complete / discovery_partial / discovery_unavailable` 及旧 `evidence_ready` | Provider 发现覆盖怎样 |
| Deployment/Target health | `healthy / degraded / unhealthy / unknown` | 已确认目标是否满足版本化检查策略 |
| Business health | 后续领域状态 | 业务维度是否有足够 Observation；不由 HOST 自动推导 |
| Retention tier | `full / hour / day / summary` | 数据保存粒度；与 freshness 无关；`summary` 仍是后续健康/事件层 |

关键例子：

- 刚采到 96% CPU 是 `fresh + critical`，不是 stale。
- SSH 本轮超时但上一份样本仍在有效期内时，页面同时显示“本轮采集失败”和“上一份样本尚 fresh”；不得隐藏失败。
- 样本超过有效期后变为 `stale`，旧值可显示为历史，但当前资源条件变为 `unknown/stale`，不继续保持绿色。
- Temperature Provider 不存在时是 `unsupported/not_applicable`；它是可选维度，不让整轮采集失败。
- systemd 单元 `inactive` 在用户尚未声明“应常驻 active”前只是 Observation，不生成项目 unhealthy。

## 4. 采样、心跳和几小时巡检的区别

### 4.1 建议起始周期

以下是首轮容量估算用的建议值，不是所有服务器的普遍真理：

| 周期对象 | 建议默认 | `stale_after` | 用途 | 明确局限 |
|---|---:|---:|---|---|
| HOST 访问心跳 | 10 分钟 | 30 分钟 | SSH/Linux 身份、boot_id、uptime | 不读取完整资源，不证明服务健康 |
| 主机资源快照 | 5 分钟 | 15 分钟 | CPU、内存、load、容量、IO、网络、进程摘要 | 会漏掉两个采样点之间的短尖峰 |
| 已确认 Target 服务状态 | 5 分钟 | 15 分钟 | systemd/container 等 typed check | 依赖 ProjectTarget 和用户声明期望状态 |
| 温度 | 15 分钟 | 45 分钟 | 支持传感器时的趋势 | 虚机常无传感器，阈值与硬件有关 |
| 部署/资产发现 | 6 小时 | 12 小时 | Docker/Compose/systemd 等库存变化 | 不适合判断短故障或瞬时资源压力 |

H2 API 允许显式选择 5 分钟至 24 小时的整数秒 interval，不引入 cron，也不自动创建默认 schedule；5–15 分钟只是尚待容量验证的资源监控建议区间，小时级主要适合低频巡检。jitter 使用保存到 schedule 的确定性正向偏移，避免大量 HOST 在整点同时连接且防止重启后改变同一时间栅格。

同一 HOST 的到期动作必须 coalesce：`host_resource_v1` 已读取 SSH/Linux 身份、boot_id 和 uptime，因此一次成功资源快照同时满足本周期的 HOST 访问心跳，不再额外建立 10 分钟 heartbeat SSH 会话。只有未启用资源监控，或资源 profile 的下次到期晚于 heartbeat freshness window 时，才单独执行轻量心跳。Target 服务检查与资源快照落在同一合并窗口时也应复用已认证会话，但 run/coverage 仍分别记录，不能因共用传输而混合健康语义。

### 4.2 为什么“每几小时检查健康”证据不足

假设每 6 小时采一次：

- 一次持续 20 分钟的 CPU/IO 尖峰大概率完全落在两个采样点之间；
- 由 `/proc/diskstats`、`/proc/net/dev` 两次计数器之差得到的是 6 小时平均值，会稀释短时拥塞；
- systemd 服务在两次采样之间重启后恢复，只能通过重启计数或外部事件间接看到；
- `succeeded` 只能表明采样时刻读取成功，不能生成“过去 6 小时一直健康”。

因此，小时级巡检适合容量、资产、版本和低频漂移；分钟级快照适合基础资源趋势；秒级尖峰、QPS、延迟分位数和短中断更适合已有 Prometheus/OpenTelemetry 等连续指标源。

### 4.3 单次快照中的瞬时值和跨周期趋势

CPU、磁盘 IO、网络吞吐都是累计计数器的差分结果。首版 SSH profile 应在同一个受控采集会话中读取两组计数器，中间固定等待约 1 秒，用于生成 `instant_1s`；同时保存原始累计计数器，与上一次周期样本生成 `period_average`。

```text
counter A → 固定短间隔 → counter B → instant rate
上次周期 counter → 本次 counter B → period average
```

两个值含义不同，API 必须带 `window_seconds`，页面不得把 1 秒瞬时值画成过去 5 分钟平均。两帧都读取 `/proc/uptime`，使用 `dt=uptime_B-uptime_A` 作为 rate 分母；APP 接收时间只定位时间线，不用易受 NTP 与 SSH 延迟影响的 wall clock 计算 rate。若 `boot_id` 改变、`dt<=0`、实体身份变化、计数器减少或时间间隔不足，本次差分质量为 `counter_reset / insufficient_interval`，不计算伪造的 0。

同一 boot、同一实体上 `current < previous` 时，现代 64 位计数器默认按 reset 处理。只有来源明确为 32 位，并且模差不超过接口/设备物理上限时，才允许用 `current + 2^32 - previous` 解释回绕；其余情况 rate 保持 unknown。`/proc/stat` 的 iowait 是例外：Linux 文档明确它可能在同一 boot 内下降，此 interval 标记 `counter_unreliable`，不据此声称重启，也不把负差值截成 0。

## 5. Linux 固定只读采集矩阵

### 5.1 通用约束

- 远程动作由服务端版本化生成，固定 `LC_ALL=C`；浏览器、模型和用户字段不传入命令字符串。
- 优先读取 `/proc` 与 `/sys`，其次使用 Linux 常见只读工具；工具缺失按指标族记录 `unsupported`，不执行安装。
- 不调用 `sudo`，不写 TARGET_HOST，不创建临时脚本或常驻进程，不改 SSH 配置。
- 原始命令输出仅在任务内解析；SQLite 保存结构化指标、质量、时间、来源和脱敏错误摘要。
- 每个动作设置本地超时、输出字节上限和条目数上限。某个指标族失败不覆盖已经成功的指标族。

### 5.2 指标与计算

| 指标族 | 首选只读来源/固定动作 | 保存的基础字段 | 派生与解释 | 失败/兼容语义 |
|---|---|---|---|---|
| CPU | `cat /proc/stat`；优先读取 `/sys/devices/system/cpu/online`，`getconf _NPROCESSORS_ONLN` 作 fallback | 每 CPU 与总计的 `user,nice,system,idle,iowait,irq,softirq,steal` 累计 tick，在线 CPU 数 | `total=各项之和`；`busy%=100*(Δtotal-Δidle-Δiowait)/Δtotal`；另存 iowait%、steal%。`guest/guest_nice` 已包含在 user/nice，不加入 total | 两次样本、同一 boot_id 且 `Δtotal>0` 才计算；普通 counter 回退为 reset；iowait 回退为 counter_unreliable |
| 内存 | `cat /proc/meminfo` | `MemTotal,MemAvailable,SwapTotal,SwapFree`，可选 `Cached,Buffers,Slab` | `used=MemTotal-MemAvailable`；以 available ratio 判断压力；cache 不是简单“已浪费内存” | 缺少 `MemAvailable` 时首版标记该派生值 unsupported，不用不透明公式猜测 |
| Load | `cat /proc/loadavg`；在线 CPU 数 | `load1,load5,load15,runnable_entities,total_scheduling_entities` | `normalized_load=loadN/online_cpu`；load 包含可运行和不可中断任务，不等同 CPU% | 第四字段通常包含线程等调度实体，不当作严格进程数；CPU 数缺失时 normalized 值 unknown |
| 磁盘容量 | 先读 `/proc/self/mountinfo`；对过滤、验证后的 mount 逐项执行固定 `df -P -k`，可选 `df -P -i`；`findmnt` 仅作可选映射 | mount、source、fstype、size/used/available KiB、inode 数 | 同时保留 size/used/available；默认 `allocatable_used_ratio=used/(used+available)`，避免忽略保留块；每个 mount 单独评价 | 逐 mount 超时才能保证部分成功；GNU/findmnt 缺失走已声明 fallback 或 unsupported；不保存 mount options |
| 磁盘 IO | `cat /proc/diskstats`；可选 `lsblk -J -b -o MAJ:MIN,KNAME,TYPE,PKNAME,MOUNTPOINTS` 做映射 | major/minor、读写次数、读写 sector、读写耗时、inflight、io_ms、weighted_io_ms | `read_Bps=Δread_sector*512/dt`，write 同理；`IOPS=(Δreads+Δwrites)/dt`；`read_await=Δread_ms/Δreads`，write 同理；`util%=100*Δio_ms/(dt*1000)`；`avg_queue=Δweighted_io_ms/(dt*1000)` | inflight 是 gauge 不做差分；Linux 5.0+ 的 io_ms 在长并发 I/O 下可能低估；NVMe/虚拟盘 util/await 不是介质饱和真值；分区/LVM 不重复汇总 |
| 网络 | `cat /proc/net/dev`；读取 `/sys/class/net/*/{ifindex,iflink,operstate,speed}`，可选 master 关系 | identity=`boot_id+ifindex`、name、rx/tx bytes、packets、errors、drops、link state/speed | 两样本按方向计算 bytes/s、packets/s、错误/丢包率；全双工 RX/TX 分别除以 speed，不把二者相加；`lo` 单独展示 | speed 缺失、-1 或虚拟接口时不算利用率；bridge/bond/veth 不跨层相加；同名 ifindex 改变视为新实体 |
| 进程摘要 | 首选 `/proc/stat` 的 `procs_running/procs_blocked` 与有界 numeric PID 枚举；procps `ps -e -o pid=,ppid=,stat=,etimes=,comm=` 仅作 fallback；Target 级读 `/proc/<pid>/stat,status` | 进程总数，R/D/Z 状态计数；受控 Target 的 pid、starttime、rss、threads | `(boot_id,pid,starttime)` 防 PID 复用；进程 CPU%= `100*Δ(utime+stime)/(CLK_TCK*dt)`，为单核尺度可 >100%；整个 unit 优先 cgroup/systemd accounting | `/proc/PID/stat` 从 comm 的末个合法 `)` 后定位字段，不能简单空格 split；不读 environ/cmdline；进程消失不让整轮失败 |
| systemd 服务 | 对受控 unit 调用 `systemctl show UNIT --no-pager --property=Id,LoadState,ActiveState,SubState,Result,NRestarts,ExecMainCode,ExecMainStatus,MainPID,InvocationID,ControlGroup,ActiveEnterTimestampMonotonic` | unit 状态、运行 invocation、cgroup、重启计数、主进程退出摘要 | policy 声明允许的 `(ActiveState,SubState)` 集合；oneshot 的 `active/exited` 可合法，不用单一 expected_active bool 粗判 | 非 systemd PID1、user unit 需不同 bus、旧 systemd 缺字段、unit 不存在和权限不足分别记录，不降级 connection |
| Uptime/重启 | `cat /proc/uptime`；`cat /proc/sys/kernel/random/boot_id`；`/proc/stat` 的 `btime` 可交叉核验 | uptime seconds、boot_id、boot time | boot_id 改变生成 `host_reboot_observed` 事件并使跨重启 counter 差分失效 | 低 uptime 本身不是 unhealthy；计划重启和异常重启需由其他事实解释 |
| 温度（可选） | `/sys/class/thermal/thermal_zone*/{type,temp}`；`/sys/class/hwmon/hwmon*/temp*_input` 及 name/label/max/crit | identity=设备 symlink/name+channel/label、摄氏度、设备 max/crit | hwmonN/thermal_zoneN 编号可重排，不单独作稳定键；按来源验证量纲，优先设备 max/crit | 传感器不存在、量纲不确定、虚机无温度或权限不足为 optional unsupported，不推断 0°C 或正常 |

### 5.3 不采集的内容

首版明确跳过：

```text
/proc/*/environ
完整进程命令行和启动参数
包内容、连接载荷与 DNS 查询内容
完整日志正文
文件系统目录遍历
SSH 配置、authorized_keys 和系统配置
任意用户/模型提供的 Shell
```

这些内容既不是基础资源指标，也可能包含凭据、个人数据或高基数标签。

## 6. 健康策略、阈值与未知状态

### 6.1 阈值不是事实

阈值依赖服务器类型、磁盘介质、工作负载、容错目标和业务时段。以下只作为首次启用时的**建议种子**；保存时必须形成版本化 policy，界面显示来源为 `recommended_default`，用户确认后才参与正式评价。

| 条件 | warning 建议 | critical 建议 | 连续性与边界 |
|---|---:|---:|---|
| CPU busy | ≥80% | ≥95% | 连续 2 个有效样本；同时展示 iowait/steal 以避免误判原因 |
| MemAvailable ratio | <15% | <5% | 连续 2 个有效样本；swap 已用量只作辅助，不能单独证明压力 |
| load5 / online CPU | ≥1.0 | ≥1.5 | 连续 2 个有效样本；高 load 可能来自 IO 等不可中断任务 |
| 文件系统 used | ≥80% | ≥90% | 每个 mount 独立；小盘还需配置最小可用字节，避免只有百分比 |
| inode used（可选） | ≥80% | ≥90% | 只对提供 inode 统计的文件系统评价 |
| 磁盘 IO 利用率/await | ≥80% 或 await≥20ms | ≥95% 或 await≥50ms | 设备差异很大，默认只展示趋势；用户确认设备策略后再告警 |
| 网络 errors+drops | ≥0.5% | ≥2% | 分母至少 1000 packets/window；低流量样本只显示计数 |
| 网络带宽利用率 | ≥80% | ≥95% | 仅 speed 可用且可信时评价 |
| systemd Target state | 不在 policy 允许状态集合持续 1 次 | `failed` 或连续 2 次不在允许集合 | 仅限用户确认的 Target；policy 显式列出允许的 `(ActiveState,SubState)`，任意发现 unit 不自动告警 |
| zombie 进程 | >0 | 由用户配置 | 默认只生成 attention；不同应用的容忍度差异大 |
| uptime | 不设阈值 | 不设阈值 | boot_id 变化是事件，不是资源健康分数 |
| 温度 | 设备 `crit-10°C` | 设备 `crit` | 无设备阈值时保持未配置，不套用通用 CPU 温度 |

紧急容量保护可以单独配置，例如文件系统 ≥98% 或可用空间低于确认的绝对下限时立即 critical；这仍只产生本地 Condition/Incident，不触发清理、扩容或远程写入。

### 6.2 抖动、恢复与事件去重

- 默认阈值只评价 `period_average`；`instant_1s` 只展示或生成单独 spike attention。policy 必须声明 `series/window/min_valid_samples/enter_count/recovery_threshold`，不得在两类窗口间隐式切换。
- 一般 warning/critical 需连续 2 个有效样本；恢复也需连续 2 个正常样本。
- 明确的 systemd `failed`、文件系统紧急阈值可按 policy 配置为单样本 critical。
- 相同 condition 连续存在时只更新 `last_observed_at` 和计数，不重复生成事件；状态改变才发 SSE。
- 阈值、要求维度或 Target 期望变更后产生新 policy revision；旧评价保留原 revision，不回写历史。
- 采集权限不足、工具缺失、输出截断、样本过期和 counter reset 产生 `unknown`，不产生 pass。

### 6.3 确定性评价规则

1. 尚无 policy：`unknown + not_configured`。
2. required 指标取得 fresh 明确 critical：范围健康为 `unhealthy`。
3. required 指标缺失、过期、权限不足或解析失败：范围健康为 `unknown`。
4. optional 指标 warning/critical：范围健康最多为 `degraded`，并保留具体 condition。
5. required 指标全部 fresh 且为 ok、没有 optional failure：范围健康才可为 `healthy`。
6. freshness 到期后，旧评价失效并转 `unknown/stale`；过期数据不得继续贡献 healthy。
7. TechnicalProject 汇总只计算用户标为 required 的 ProjectTarget，并同时返回 coverage；Business 汇总后置。

首屏优先展示各 condition、unknown 维度和 attention 数量，不制造一个掩盖覆盖缺口的“综合健康分”。

## 7. 建议数据模型

保持 Rust 单体和 SQLite，不为首个周期观察引入 Redis、消息队列、通用 `jobs/job_attempts` 或时序数据库。

### 7.1 周期与运行

```text
monitor_schedules
  schedule_id
  host_id
  profile = host_heartbeat_v1 | host_resource_v1 | inventory_discovery_v1
  interval_seconds / jitter_seconds / stale_after_seconds
  required_families_json / optional_families_json
  state = enabled | paused | archived
  next_due_at / last_due_at
  revision
  lease_token? / lease_until?
  created_at / updated_at
  UNIQUE(host_id, profile)

monitor_runs
  run_id / schedule_id? / host_id
  trigger = scheduled | manual | catch_up
  state
  scheduled_for / started_at / finished_at
  collector_version / boot_id?
  coverage_json
  output_bytes
  failure_code? / failure_summary?
  request_sha256? / idempotency_key?
```

`UNIQUE(schedule_id, scheduled_for)` 保证同一个到期点只物化一次。单 HOST 同时只允许一个资源采集 run；人工运行优先，周期重叠记录 `skipped_overlap`，不暗中排队无限补跑。

### 7.2 指标、评价与历史

```text
metric_samples
  sample_id / run_id / host_id
  subject_kind = host | filesystem | block_device | interface | process | service | sensor
  subject_id
  metric_name
  dimensions_json（受控低基数）
  sample_kind = gauge | counter | derived
  value_real? / value_integer? / unit
  window_seconds?
  quality
  observed_at
  source_kind（受控枚举，不保存远程 URL）
  UNIQUE(run_id, family, subject_kind, subject_id, metric_name, dimensions_sha256, sample_kind, source_kind)

health_policy_versions
  policy_id
  scope_kind = host | project_target
  scope_id
  revision / state = active | superseded
  thresholds_json（DTO 校验后的受控 schema）
  policy_sha256
  created_by / created_at

health_evaluations
  evaluation_id / run_id / policy_id / policy_revision
  scope_kind / scope_id / condition_key
  status = ok | warning | critical | unknown | stale
  reason_code
  observed_at / valid_until
  evidence_refs_json / input_sha256

metric_rollup_partitions
  partition_id / host_id
  resolution = hour | day
  bucket_start / bucket_end（UTC）
  input_count / input_digest / series_count
  state = complete | sealed
  compacted_at / sealed_at / rollup_rows_pruned_at?
  UNIQUE(host_id, resolution, bucket_start_epoch_ms)

metric_rollups
  rollup_id / partition_id / host_id
  family / subject_kind / subject_id / metric_name / dimensions_sha256
  sample_kind / source_kind / unit / resolution / bucket_start / bucket_end
  sample_count / observed_count / non_observed_count
  expected_count? / missing_count? / reset_count
  min / max / average / p95 / last / counter_delta?
  quality / quality_counts_json / input_count / input_digest
  boundary_sample_id? / last_sample_id / last_run_id / last_sample_at

monitoring_history_maintenance / monitoring_compaction_runs
  runtime state / configured retention / last success or error
  per-run hour/day partitions and raw/hour/day deleted counts
  current raw/hour/day row counts / database bytes
```

- `monitoring_current`、HOST 当前 condition 与 coverage 优先通过最新样本/评价读模型生成，不急于复制当前状态表。
- observed gauge/derived 恰好使用 `value_real`，observed 累计 counter 恰好使用 `value_integer`；非 observed 样本两者都为空。累计值保持整数，避免在 H3b 做 delta 前先丢失精度。
- counter rollup 保存 delta/reset_count，不对累计 counter 本身求平均。
- hour/day 只处理已经闭合的 UTC bucket；同一分区以 `input_count/input_digest` 审计输入并幂等 upsert。当前 bucket 等下一轮闭合后再处理，不被当作完整区间。
- `GET /api/v1/monitoring/status` 同时返回 compactor runtime、最近运行结果、raw/hour/day 行数、数据库字节和当前 retention 配置；该维护状态只描述 APP_HOST 本地 SQLite，不是 TARGET_HOST 健康。
- state/condition rollup 保存每种状态计数、最差状态与缺口，不把 unknown 当作 0。
- `health_incidents`、acknowledgement 与外部通知放到告警切片；用户 ack 不反写健康评价。
- ProjectTarget 健康表在 Deployment/ProjectTarget 持久化后启用；HOST 指标切片不提前伪造项目健康。

### 7.3 调度器恢复

首版使用进程内 Tokio scheduler + SQLite 租约：

- 单实例每次 tick 领取到期 schedule，事务内写 lease 和 run；
- 进程重启时把遗留 `running` 标记 `interrupted`；
- 默认最多补一个仍在 freshness window 内的过期周期，不回放所有错过周期；
- backlog、oldest_due_at、last_tick_at 形成 scheduler 状态，但它不是 TARGET_HOST heartbeat；
- 同一 HOST 的 discovery 与 resource run 使用明确互斥策略，避免 SSH 洪峰；资源 run 不复用“成功即产生 ProjectionDraft”的 discovery API。

## 8. 保留、降采样和容量

### 8.1 当前配置默认值与启用边界

| 数据 | 配置默认值 | 生效条件 |
|---|---:|---|
| observed raw metric samples | 7 天 | `NETWORK_ATLAS_MONITOR_RETENTION_ENABLED=true` |
| 非 observed quality raw samples | 30 天 | 同上；包括 unsupported/parse_failed/reset/permission/timed_out 等，不等同尚未实现的健康 warning/critical |
| hour rollup | 90 天 | 同上；清理前必须已有对应 day 分区 |
| day rollup | 365 天 | 同上 |
| 每个 scope 的 latest observation/evaluation | scope 存续期间 | H3c 已实现；随 monitor run 级联删除 |
| policy versions、incident、ack | policy versions 随 HOST 手动删除；incident/ack 后续 | H3c policy 已实现，incident/ack 后置 |
| 原始 SSH 输出、完整日志和指标端点原文 | 任务内临时处理，不进入长期库 | 与 retention 开关无关 |

现有 Discovery 保留策略保持：每 HOST 最近 3 次完整脱敏 Evidence，更早只留摘要、哈希、时间和差异。监控 raw/rollup 是独立保留层，不把发现 Evidence 当作高频时序库。

H3b 的 rollup 与周期 compactor 已启用，但**自动删除默认关闭**。`retention_enabled=false`
时 compactor 仍生成 hour/day、写维护账本并统计容量，raw/hour/day 行均不自动删除。只有进程
启动时读取到显式 `NETWORK_ATLAS_MONITOR_RETENTION_ENABLED=true` 才进入删除分支；再次
关闭只停止后续删除，不能恢复已删除历史。SQLite 删除后的页通常留在数据库内复用，不承诺
文件立即缩小。

新增环境变量及层级约束：

| 变量 | 默认值 | 允许范围/约束 |
|---|---:|---|
| `NETWORK_ATLAS_MONITOR_COMPACTOR_TICK_SECONDS` | 3600 | `60..86400` 秒；启动时另有一次立即 catch-up |
| `NETWORK_ATLAS_MONITOR_COMPACTOR_PARTITIONS_PER_TICK` | 32 | `1..1024`；每轮分别作用于 hour 与 day |
| `NETWORK_ATLAS_MONITOR_RETENTION_ENABLED` | false | 只接受显式布尔 opt-in；控制删除，不关闭 rollup |
| `NETWORK_ATLAS_MONITOR_RETENTION_DELETE_BATCH_SIZE` | 5000 | `1..100000`；限制每轮 raw 删除总数 |
| `NETWORK_ATLAS_MONITOR_RAW_OBSERVED_RETENTION_DAYS` | 7 | `1..365` |
| `NETWORK_ATLAS_MONITOR_RAW_NON_OBSERVED_RETENTION_DAYS` | 30 | 不少于 observed raw，最多 730 |
| `NETWORK_ATLAS_MONITOR_HOUR_RETENTION_DAYS` | 90 | 不少于 non-observed raw，最多 3650 |
| `NETWORK_ATLAS_MONITOR_DAY_RETENTION_DAYS` | 365 | 不少于 hour，最多 7300 |

配置在 APP 启动时读取；调整后需要重启。层级约束由解析器逐层应用，无效或越界输入回落到
对应默认/约束范围，而不是让进程带着不一致 retention 启动。正式 opt-in 前必须先验证加密
备份、恢复、查询窗口、实际 SQLite 增量和 APP_HOST 磁盘余量。

### 8.2 降采样约束

1. bucket 使用 UTC 固定边界，并记录 observed/non-observed、nullable expected/missing 与 quality count；schedule provenance 不完整时不制造 expected/gap。
2. 先在事务中写入幂等 rollup，核对 `input_count/input_digest`；只有 retention 显式启用、所有闭合分区积压已追平，且同一 raw 已被完整、sealed 的 hour 与 day 分区覆盖后，才分批删除 raw。积压存在时整轮暂停删除，避免丢失后续 counter bucket 所需的边界样本。
3. compactor 重复执行结果一致；失败只产生 APP 维护 attention，不改变 TARGET condition。
4. `retention_tier` 只说明保存粒度；`freshness` 只由观察时间和 policy 窗口决定。
5. 查询 `resolution=raw/hour/day` 直接读取对应 tier；`resolution=auto` 按请求跨度选择一个实际 tier（不跨 tier 拼接），并返回 actual resolution、keyset cursor 与 rollup 统计。raw 点按观测时刻落入 `[from,to)` 选择；hour/day bucket 按时间区间与 `[from,to)` 相交选择，避免监控起点位于首个 bucket 内时误漏该聚合点。当前范围上限分别为 raw 7 天、hour 366 天、day/auto 3660 天；范围上限不等于 retention 保证。
6. 最近有效样本和当前 policy 不随 raw 清理丢失。

### 8.3 成本预算

单个 HOST 每日理论运行数：

```text
5 分钟资源快照 = 288 个到期点/日（已包含心跳）
10 分钟独立心跳 = 144 个到期点/日（仅未启用资源监控时）
6 小时资产发现  =   4 个到期点/日
```

不要把 288 次资源快照和 144 次心跳直接相加。启用 5 分钟资源快照时，单 HOST 基础 SSH 预算约为 `288 + 4 = 292` 个到期会话/日；只启用 10 分钟心跳与 6 小时发现时约为 `144 + 4 = 148` 个到期会话/日。同一合并窗口内的 Target 检查和发现是否可复用会话，必须在实现后按实际审计记录计算，不能预先假定为零成本。

未合并前的理论到期数近似为 `HOST 数 × 86400 / interval_seconds`；实际 SSH 会话数应由 coalescer 审计并返回。首版必须：

- 每个 profile 尽量复用一个 SSH 会话批量读取固定源；
- 单 HOST 并发为 1，全局默认并发上限建议为 4，并可配置；
- 使用 jitter、超时、输出上限和低基数 dimensions；
- 将同一 HOST 合并窗口内的 heartbeat/resource/Target typed checks 组合为一次已认证会话，并分别保存各 profile 的结果；
- UI 在保存 schedule 前显示预计每日 SSH 次数与 raw 数据量；
- 当 HOST 数量、留存或查询延迟持续超过 SQLite 预算后，再以真实指标评估已有 Prometheus Adapter 或其他存储，不预先换数据库。

H3b compactor 不产生 SSH 成本，但会在 APP 启动时立即运行一次，并在每个 tick 扫描闭合
分区、计算统计/digest、写 rollup 和维护账本。默认上限是每轮最多 32 个 hour 加 32 个 day
分区；积压较大时需要多轮追平。缩短 tick、提高 partitions 或放大 raw 删除 batch 都会增加
APP_HOST 的 SQLite 锁竞争、CPU、WAL、磁盘 IO 与备份体积波动。`database_bytes` 是 SQLite
页数估算，不等价于可立即归还给文件系统的空间；生产预算必须以真实运行数据校准。

读取已有 Prometheus 可以降低逐 HOST SSH 频率并提高时间分辨率，但新增了指标端点鉴权、TLS、标签基数、PromQL 模板、Prometheus 自身可用性和数据保留的运维成本。

## 10. 权限、安全和失败语义

### 10.1 权限边界

- 继续要求有效 OwnerSession、工作区归属、已确认主机指纹和有效 SecretRef。
- 首版新增的唯一能力是 `observe_host_metrics`，仍属于 fixed typed read-only；不开放任意 Shell、sudo、安装 exporter、写配置、重启或清理。
- Project Agent 只能通过明确 ProjectTarget 调用 target 级监控工具；HOST 全局指标按授权提供摘要，跨项目私有细节需显式授权。
- 密码、私钥、Token 和完整凭据正文不进入 API、日志、SSE、SQLite、导出或 Agent 上下文；SQLite 只在既有凭据配置边界保存 SecretRef 描述，监控样本和响应不返回 `credential_ref` 或秘密路径。
- Prometheus labels 可能携带主机名、路径、租户或 URL；只保存白名单标签并做秘密模式脱敏。

### 10.2 失败分类

| code | 含义 | 状态影响 |
|---|---|---|
| `MONITOR_ALREADY_RUNNING` | 同 HOST 已有互斥运行 | 新 run=`skipped_overlap`；旧 run 不受影响 |
| `MONITOR_SCHEDULE_PAUSED` | schedule 未启用 | 不启动 SSH；返回领域冲突 |
| `SSH_UNREACHABLE` | 网络/SSH 服务不可达 | monitor run failed；资源 condition unknown；连接轴记录自己的观察 |
| `SSH_AUTH_FAILED` | 登录凭据被拒绝 | 同上；不归为资源 critical |
| `HOST_KEY_CHANGED` | 主机身份变化 | 停止采集并要求复核；不绕过严格校验 |
| `COLLECTOR_PERMISSION_DENIED` | 单个固定源无读取权限 | 对应 family unknown；其他 family 保留 |
| `COLLECTOR_UNSUPPORTED` | `/proc`/工具/传感器缺失 | required→partial/unknown；optional→not_applicable |
| `COLLECTOR_TIMED_OUT` | 单动作或整轮超时 | 对应 coverage unknown；保留已成功项 |
| `COLLECTOR_OUTPUT_LIMIT` | 输出超过条目/字节上限 | 截断数据不可参与完整评价 |
| `COLLECTOR_PARSE_FAILED` | 输出不符合版本化 parser | 对应 family unknown，并记录脱敏摘要 |
| `COUNTER_RESET` | 重启、接口重建或计数回退 | 样本仍保存，rate unknown；不把负差值变为 0 |
| `CLOCK_SKEW` | HOST 与 APP_HOST 时间偏差超出政策 | 使用 APP 接收时间并标记质量，不能静默改时间线 |

一轮中所有 required family observed 才是 `succeeded`；至少一项成功但 required 有缺口为 `partial`；无 required family 可用为 `failed`。optional temperature unsupported 不单独把完整轮次降级。

监控 SSH 失败可以追加新的连接 Observation，但健康 evaluator 只把资源状态置为 unknown；它不得把 Provider/服务失败改写为 `SSH_AUTH_FAILED`，也不得让 TARGET 状态影响 APP `/healthz`。

## 11. 页面语义

`#scope=global&view=hosts` 是**服务器状态页**，不是健康历史页、业务页或全局资源关系页。页面信息优先级固定如下：

1. **主内容：当前服务器状态快照。** 首屏回答“这台服务器现在怎样”，突出最新 CPU、内存、load、磁盘容量与 IO、网络吞吐、uptime、进程摘要及可用的温度信息；每项必须同时显示采样时间、fresh/stale/unknown 和 coverage，避免把旧样本伪装成实时值。
2. **辅助状态：连接与采集可信度。** SSH 连接、monitor schedule、最近 monitor run、最近资产发现和 Provider coverage 用于解释当前数据能否相信，但不抢占资源指标的主视觉层级。
3. **次要内容：健康历史。** 紧接当前状态区域下方，以较矮、留白更大的时间带概括近期状态；默认不占满首屏，也不替代当前指标卡。趋势细节通过展开或 drill-down 查看。
4. **页面排除项。** 不在服务器页呈现 Business 看板、服务器—项目—服务空间关系画布或具体项目投影工作台；它们分别属于 `global/world`、`global/resource` 和 `scope=project`。

当前状态的视觉验收不是“字段都出现”即可：CPU、内存和容量至少同时提供醒目的当前值、单位、可比较的长度/填充和状态标签；网络明确上下行；load 明确核数参照；磁盘按 mount 展示而不是只给一个平均值。异常、未知和 stale 必须在不阅读说明文字时就能凭位置、形状/图标和状态色被发现。颜色不得成为唯一编码，无确定上限的指标不得使用暗示百分比的仪表环。

每台服务器至少展示：

```text
SSH 连接状态与 last_success_at
监控 schedule 是否启用/按时
最近 monitor run 及 coverage
资源样本 freshness
CPU / 内存 / load / 容量 / IO / 网络当前值与短趋势
warning / critical / unknown condition
最近资产发现与 Provider coverage
```

- 当前快照卡是首屏视觉主角；不得用大面积健康历史、关系图或候选绑定工作台挤压它。所谓“当前”仍是最近一次观测，必须显示准确时间和 freshness，不宣称浏览器正在读取远端实时流。
- 趋势图必须显示采样点和 gap，不用平滑线掩盖缺失数据。
- 健康总览时间带只提供 `24h / 7d / 30d` 三个首版窗口，默认分别聚合为 `24 / 28 / 30` 个可视 bucket，即 `1h / 6h / 1d`；不把每个 raw sample 画成密集条纹。精细 raw/hour 曲线只在详情 drill-down 展示，后端返回实际 bucket 宽度，前端不自行猜分辨率。
- 每个 bucket 返回 `ok_count / warning_count / critical_count / unknown_count / expected_count / observed_count / coverage / gap_count`。`worst_status` 只用于快速摘要，不能覆盖计数或 unknown；tooltip 必须解释时间范围、状态计数、覆盖、缺口、来源 resolution 和 policy revision。
- 时间带使用有间距的大圆角段，颜色固定为绿/黄/红/灰，同时提供图标、纹理或文字等非颜色标识；unknown/gap 不得使用绿色。键盘焦点、屏幕阅读器标签与高对比度模式必须能读出同样信息。
- 小时级巡检页面明确写“最近采样/区间未知”，不显示“全天正常”。
- 点击磁盘、接口、服务或传感器显示来源、时间、窗口、quality 和 policy revision。
- 项目资源页在 ProjectTarget 落地后展示 Target health 和相关 HOST condition 引用；不复制整台 HOST 的所有指标。
- 全局业务网不因 HOST 资源 ok 自动把 TechnicalProject/Business 节点变绿。
- `global/resource` 独占 HOST、TechnicalProject、Deployment/服务和 ResourceEntity 的跨对象关系表达；服务器页可以显示数量摘要并链接过去，但不复制关系画布。
- 具体项目投影只出现在 `scope=project` 导航项下；服务器发现产生的候选可以从服务器页进入独立审查动作，但不得把候选审查伪装成已存在的项目投影。
- Grafana 可作为已有监控系统的深度链接或 Adapter 来源，但 Network Atlas 不复制其任意 dashboard 配置。

### H3a：可信 raw 历史（已实现）

- 迁移 `0011_monitoring_history.sql` 新增 append-only `metric_samples`、raw history metadata，并为 scheduled run 固化 `due_interval_seconds / missed_due_count`；八个 family 的 availability 自然键相互独立。第二帧 CPU aggregate/per-core、block device 与 interface 累计 counter 使用 `value_integer` 保存；CPU observed counter 必须同时有 run `boot_id`，磁盘/网卡 subject identity 直接包含 boot identity。
- terminal run、真实 quality samples 与 `monitoring_current` 在同一事务写入；failed run 保留失败 quality 历史，但不替换上一份有效 current；重复完成不追加第二份历史。
- H3a 首次交付时 `GET /api/v1/hosts/{host_id}/metrics` 只开放 `auto/raw`；H3b 现已在同一接口开放 `raw/hour/day/auto`。查询继续使用 epoch millisecond 的 `[from,to)` 边界，默认只读 HOST aggregate；typed subject/metric/sample filters 负责下钻。raw 每页按 `(observed_at_epoch_ms, sample_id)`，hour/day 每页按 `(bucket_start_epoch_ms, rollup_id)` 做 keyset 排序；`limit=1..5000`，均用成对 cursor 遍历，不再使用不可继续的全局 50k/series 截断。
- 每个点返回 `sample_id / run_id / at_epoch_ms`；counter 同时返回便于绘图的 `value` 和无精度损失的十进制 `value_integer` 字符串。`latest_observation_at` 与 `latest_valid_sample_at / latest_valid_until / freshness` 分开，避免用旧正常值遮盖最近失败。
- `expected_count / gap_count / coverage` 在 schedule-version provenance 尚不完整时保持 `null`，`provenance_complete=false`；unknown 不折算为连续正常。
- 只从 schema 11 上线后开始积累样本，不从 current 快照回填。H3a 边界不执行自动清理；H3b 虽已实现安全删除路径，默认仍保持 retention 关闭，避免未显式 opt-in 就不可逆删除真实数据。
- 普通 HOST/workspace JSON 导出通过 content manifest 明确声明 raw 默认不内嵌，scope 行数只是在 manifest 生成时取得的提示值；调用方可按 HOST、六种 subject kind、7 天半开窗口和 cursor 分页取得语义化 metric points，但这些 live query 不构成固定数据库快照，也不包含重建 `metric_samples` 原始行所需的全部字段，因此 `lossless=false`、`complete_export=false`，不得用返回点数与提示行数相等来证明完整。删除前生成并验证的 SQLite backup 才是完整恢复载体；它包含 history metadata 与全部现存 raw，并验证数据库哈希和可读性。
- HOST/workspace 删除先关闭 manual/discovery/schedule 与 scheduler tick 的 observation admission，再取得全部 observation permits；已进入的 worker 完成 terminal transaction 后才备份，闸门一直持有到 cascade commit，避免 backup 与删除之间丢失新 schedule/run/sample/current。
- 文件系统远程 source 不进入 dimensions、subject id、SQLite 或 API；接口 operstate 不作为数值序列维度；非正 counter window 保存为 `NULL`。

### H3b：hour/day compaction 与周期保留（已实现；retention 默认关闭）

- **代码事实**：独立迁移 `0012_monitoring_rollups.sql` 新增 `metric_rollup_partitions / metric_rollups / monitoring_history_maintenance / monitoring_compaction_runs`；v11→v12 只增加空 rollup/维护结构，不从既有 raw 伪造迁移时历史。
- **代码事实**：compactor 以闭合 UTC hour/day bucket 为单位，从 raw 计算 gauge/derived 的 min/max/average/p95/last、quality counts，以及 counter 的 exact integer delta/reset count；分区保存 `input_count/input_digest`，重复运行幂等，候选读取期间出现并发 terminal observation 时留到下一 tick 重试。
- **代码事实**：进程启动时执行一次立即 catch-up，之后按 `NETWORK_ATLAS_MONITOR_COMPACTOR_TICK_SECONDS` 周期运行；每轮分别限制 hour/day 分区数，重启把遗留 running compaction 标为 `interrupted`。运行账本和 `/api/v1/monitoring/status` 暴露最近结果、错误、行数、数据库字节和生效设置。
- **代码事实**：`GET /api/v1/hosts/{host_id}/metrics` 已支持显式 `raw/hour/day` 和 `auto`；auto 按跨度选择一个 actual resolution，所有 tier 沿用 typed filters 与 keyset pagination。hour/day bucket 用区间相交语义选择，point 明确携带 bucket 边界、宽度、样本/quality 计数、统计值与 input digest；不把 aggregate 伪装成 raw，也不跨 tier 拼接。
- **代码事实**：retention 引擎已实现，但 `NETWORK_ATLAS_MONITOR_RETENTION_ENABLED` 默认 `false`。显式启用后，闭合分区 compaction backlog 未追平时 retention 暂停；追平后 raw 必须同时被 sealed hour/day 分区覆盖才按 batch 删除，hour 清理依赖对应 day 分区，day 再按独立上限清理。关闭开关不删除任何历史，但也不会撤销先前删除。
- **尚待运行决策**：本节不等于已完成全仓回归、24 小时多 HOST 容量验收或 Linux 正式部署验收。正式 opt-in 前仍需恢复演练、磁盘余量、WAL/查询延迟与实际 retention 预算证据。

### H3c：HOST 健康策略与时间带（已实现；schema 13）

- `GET/PUT /api/v1/hosts/{host_id}/health-policy` 提供版本化、ETag/`If-Match: revision-N` 的 HOST policy；启用策略至少有一个 `required` 条件，规则只允许 CPU collector-window、同一 run 的 MemAvailable ratio、normalized load5 和按 mount 稳定 subject 的文件系统 allocatable-used ratio。未知字段、period-average CPU、NaN/Inf、重复 mount、越界阈值和不精确的绝对字节阈值均拒绝。
- run admission 固定 `schedule_version_id` 与 `health_policy_version_id`；terminal run、typed raw samples、current snapshot 和 health receipt 在同一事务内提交。失败、超时、重叠跳过和中断都写入 `observation_state=none` 的 unknown receipt，不会沿用旧绿色结论。
- evaluation 只消费同一 run 的 samples；required critical 为 `unhealthy`，required unknown 为 `unknown`，required warning 或 optional warning/critical 为 `degraded`，所有 required fresh/ok 且无 optional failure 才为 `healthy`。unknown/gap 会打断 streak，policy revision 会重置 streak；`valid_until` 到期只在读取时派生 `stale`，不改写历史。
- `GET /api/v1/hosts/{host_id}/health?window=24h|7d|30d` 返回当前健康与固定 UTC 时间带：24×1h、28×6h、30×1d。计数单位是 `scope_evaluations`，`expected_count` 按 schedule-version due grid 计算；显式 unknown 与无 evaluation 的 `gap_count` 分开，catch-up 只计 `late_observation_count`，不回填旧 due slot。legacy baseline 之前的区间返回 `provenance_complete=false` 且 coverage/gap 为 `null`。
- 普通 HOST/workspace JSON 导出保留 health condition 的结构化结论、`evidence_ref_count` 和空的 `evidence_refs`，不泄露默认排除的 raw sample 标识；删除前经过校验的 SQLite backup 仍逐字保留完整 raw 和 evidence reference，作为唯一无损恢复载体。
- H3c 边界仍是 HOST：不把 H3b rollup 平均值当健康输入，不生成 ProjectTarget/service/port、Prometheus、incident/notification 或受控操作健康结论。

## 13. 可执行验收

### 13.1 语义与采集矩阵

| 场景 | 必须得到的字面结果 |
|---|---|
| Docker/Compose unavailable，Linux `/proc` 可读 | `connection_state=connection_ready`；host resource run 可 `succeeded/partial`；Docker Provider 状态保持独立 |
| CPU fixture 两组已知 tick | busy/iowait/steal 差分与手算一致；不重复计算 guest |
| 同一 boot 内 iowait 计数下降 | quality=`counter_unreliable`；不声称 reboot，不截成 0 |
| wall clock 跳变但 `/proc/uptime` 单调 | rate 使用 uptime 差保持正确；observed_at 标记 clock quality |
| boot_id 改变或 counter 减少 | rate quality=`counter_reset`，无负速率、无伪 0 |
| MemAvailable 缺失 | memory derived quality=`unsupported`，不使用未声明回退公式 |
| 一个网络接口在两样本间消失 | 该接口 rate unknown；其他接口和 family 仍保留 |
| 同名网络接口 ifindex 改变 | 生成新 interface identity，不跨实体计算 rate |
| 虚机无 thermal/hwmon | temperature=`not_applicable/unsupported`；required family 完整时 run 仍可 succeeded |
| 网络挂载导致 `df` 超时 | disk_capacity family partial/unknown；CPU、内存等已成功 family 不丢失 |
| 进程在采样中退出 | 记录 bounded race；整轮不因 ENOENT 失败；不读取 environ/cmdline |
| 未配置 health policy | condition/health=`unknown + not_configured`，页面无绿色健康结论 |
| fresh CPU critical | freshness=`fresh`、condition=`critical`；不是 stale |
| required 指标过期 | health=`unknown`、freshness=`stale`，旧值只作历史显示 |
| 6 小时巡检之间注入并恢复短故障 | 系统不声称该区间 healthy；显示为未观察区间 |
| systemd unit inactive 但没有 expected policy | Observation 保留，assertion=`not_applicable/unknown` |
| expected active unit 从 active→failed | 按 policy 达到连续条件后只产生一次 condition change |

### 13.2 调度与恢复

| 场景 | 必须得到的字面结果 |
|---|---|
| 两个 scheduler tick 同时领取同一 due time | 只有一个 `(schedule_id,scheduled_for)` run |
| 5 分钟资源快照与 10 分钟 heartbeat 同时到期 | 只建立一次 SSH 会话；资源快照结果分别满足 resource 与 heartbeat coverage，审计可证明未重复认证 |
| 人工资源采集正在运行 | 周期 run=`skipped_overlap`；人工 run 不受影响 |
| APP 在 run 中崩溃并重启 | 遗留 run=`interrupted`；最多补一个符合规则的周期；不洪泛补跑 |
| APP 停机超过 stale_after | metric freshness=`stale`、resource health=`unknown`；HOST 不自动变 SSH auth failed |
| 相同 condition 连续 10 次 | 只有一次状态变化事件；样本和 last_observed_at 正常追加 |
| schedule 更新带旧 revision | 返回 412；现有 schedule 未被覆盖 |
| 重复 Idempotency-Key、相同请求 | 返回同一 run/schedule；不同 payload 返回冲突 |

### 13.3 保留、安全和兼容

| 场景 | 必须得到的字面结果 |
|---|---|
| compactor 连续执行两次 | rollup 行数、input_count 和 digest 不变，无重复 bucket |
| raw 删除前 rollup 写入失败 | raw 仍在；current observation 可读 |
| 分别请求 raw/hour/day，或使用 auto | 响应返回单一 actual resolution；hour/day 带 aggregate statistics，不跨 tier 拼成伪精度曲线 |
| retention 未显式启用 | compactor 继续生成 rollup 和容量账本；raw/hour/day deleted count 均为 0 |
| retention 启用后再次关闭 | 后续 tick 不再删除；先前删除的数据不自动恢复 |
| 请求携带 `command`、任意 PromQL 或未允许 family | 400；没有 SSH 子进程或外部查询启动 |
| SSH 凭据/模型 Key/Prometheus Token | SQLite 仅保存受控 SecretRef 描述；API、SSE、日志、导出和测试产物均无秘密正文、`credential_ref` 或引用路径 |
| TARGET resource critical | `/healthz` 仍仅由 APP+SQLite 决定，不返回远端故障 |
| 旧数据库 additive migration | `foreign_key_check` 空结果、`integrity_check=ok`；旧 HOST、Discovery、OpenAPI 和 JSON 保持兼容 |
| 旧 Discovery 第 4 次完整结果后 | 最近 3 次完整 Evidence 仍可读；更早为 summary；监控 rollup 不受其清理影响 |

## 14. 进入实现前的决策门

1. 首批真实 HOST 数、可接受的每日 SSH 连接数、全局并发和 SQLite 增量预算；
2. 资源默认周期选 5、10 还是 15 分钟，以及目标故障持续时间；
3. 哪些文件系统、块设备、接口和服务进入 required scope，如何避免 LVM/容器/虚拟设备重复计数；
4. 哪些阈值由用户确认，哪些仅作未启用建议；不同 HOST class 是否需要不同 policy；
5. 是否已有 Prometheus，只读入口、租户、TLS、鉴权、保留和 metric/label 约束是什么；
6. Deployment/ProjectTarget 迁移何时完成，首批 target health check 是 systemd、container 还是受控端口；
7. Incident 只在 UI 聚合还是需要邮件/IM；通知前必须先验证去重、抖动、恢复和 rate limit；
8. 温度、进程明细和网络接口名称是否属于所需资产范围，以及它们的隐私/高基数成本。
9. H3b retention 何时从默认关闭改为显式 opt-in；启用前必须给出恢复演练、APP_HOST 磁盘余量、SQLite/WAL 增长、查询窗口和删除 batch 的真实证据。

H1 已完成一次真实 Linux HOST 成本验收，H2 已实现显式配置、默认不创建 schedule 的最小 interval 调度器。H3b 已具备本地 rollup 与 opt-in retention 的代码路径，但没有因此获得生产容量结论。最小下一步仍是在受控 HOST 上用 24 小时运行量验证约 4 秒/8,844 bytes 的单样本是否有代表性，并记录 compactor 的分区积压、SQLite/WAL 增量、查询延迟和备份恢复成本，再决定正式默认间隔、并发与是否启用 retention；不要直接部署完整 Prometheus 栈或把当前实现扩张成通用调度平台。
