# 运维项目发现与服务器页面规格

- **状态**：下一阶段实施规格，作为当前 MVP-1 之后的对象与页面基线
- **版本**：0.2
- **日期**：2026-08-14
- **适用范围**：Linux HOST 的只读运维发现、部署归属整理、项目 Agent 目标绑定和服务器资产页面
- **前置文档**：01-需求文档.md、05-最小领域模型与权限语义.md、08-前后端API与数据架构草案.md、10-HOST-SSH初始化与Agent配置规范.md

> 本文解决“服务器上到底发现什么、如何组合成业务、Project Agent 对什么负责、服务器页面显示什么”。它不把代码开发、任意 SSH Shell 或远程写入提前放进运维域。

> **当前实现边界（2026-08-14）**：本轮继续读写旧 `Project` / `ProjectionDraft` 投影契约，只增加 Provider 选择、聚合状态和服务器资产读模型。本文的 `TechnicalProject` 与 `ProjectTarget` 是后续模型迁移目标，不是本轮已落库或已开放的 API 保证。

## 1. 先校正三个前提

1. **服务器上可直接观察的是部署和资源，不是业务。** 业务归属来自用户确认的本地关系，Agent 只提出带证据的建议。
2. **Docker 只是一个 Provider。** Docker/Compose 缺失时，SSH 连接仍然可以是 connection_ready，其他 Provider 继续尝试并分别记录覆盖范围。
3. **候选不等于确认项目。** 发现器输出的是部署候选；确认 TechnicalProject 和 Business 关系是后续人工投影步骤。

## 2. 规范层级

    Business（业务）
    └── TechnicalProject（运维项目 / Project Agent 责任范围）
        └── ProjectTarget（项目目标绑定）
            ├── HOST（全局服务器）
            └── Deployment（部署实例）

### 2.1 Business

Business 表示用户关心的业务结果，可以跨多个 TechnicalProject、HOST 和 Deployment。它是语义分组和跨项目策略范围，不要求存在一个独立的 Business Agent 实例。

### 2.2 TechnicalProject

TechnicalProject 是后续模型中一个 Project Agent 的运维责任单元，例如订单 API、前端站点、异步 Worker。一个 TechnicalProject 可以跨多台 HOST；一个 HOST 也可以承载多个 TechnicalProject。

当前本地 `Project` 投影只是兼容载体，不预设它已与 TechnicalProject 一对一迁移。确认之前只存在草稿和候选，不自动创建正式业务项目。

### 2.3 HOST

HOST 是全局基础设施连接对象，登记 SSH 地址、端口、用户、主机指纹、连接状态和 Provider 能力。HOST 不拥有业务归属；项目通过 ProjectTarget 引用它。

### 2.4 Deployment

Deployment 是 HOST 上可以独立观察的部署/运行单元，常见类型包括：

    compose_stack
    compose_service
    systemd_unit
    pm2_app
    process_group
    endpoint_binding

容器、镜像、网络、卷、端口和文档仍是 Evidence 或资源实体。它们只有在证据表明属于同一个运行单元时，才通过关系连接到 Deployment。

Deployment 不直接保存单值 project_id。同一个外部部署可能暂未归类、被用户重新绑定，或作为共享运行单元被多个项目引用。

推荐最小字段：

    deployment_id
    host_id
    provider_kind
    external_id
    identity_key
    target_ref
    target_kind
    runtime_refs[]
    evidence_refs[]
    coverage
    observed_at
    freshness
    state
    warnings[]

### 2.5 ProjectTarget

ProjectTarget 是 Project Agent 操作时使用的稳定目标绑定，不是新项目，也不是新服务器。它把一个 TechnicalProject 映射到一个具体 Deployment、HOST 和适配器范围。

    project_target_id
    project_id
    deployment_id
    host_id
    target_kind
    adapter_kind
    runtime_binding
    capabilities[]
    approval_policy
    baseline_ref?
    last_observed_at
    state

例如：

    订单 API
    ├── TARGET_1 = HOST_A + systemd order-api.service
    └── TARGET_2 = HOST_B + compose order-prod / api

Project Agent 接到“检查订单 API”时，必须读取或选择 ProjectTarget，不能仅凭项目名称猜测 HOST 或服务。

### 2.6 CodeWorkspace 的边界

CodeWorkspace 不属于当前运维核心对象。专用开发 Agent 管理代码仓库、分支、测试和提交；运维域只按需保存 release_id、image_digest、commit_sha 等部署版本元数据，用于观察运行版本和漂移。

## 3. 候选与证据生命周期

为避免重复建模，DeploymentCandidate 作为 Deployment 的待确认状态/投影名称，落库共用 `deployments` 的稳定记录，不单独建立 ProjectCandidate 或候选副本表。API 可以提供按状态过滤的 `/deployment-candidates` 读模型。

    DeploymentObservation
        ↓
    DeploymentCandidate（observed / unassigned）
        ↓ 用户绑定、合并或拆分
    Deployment（linked / confirmed）
        ↓
    ProjectTarget

状态约束：

| 状态 | 含义 |
|---|---|
| observed | 本次扫描刚观察到，尚未进入人工整理 |
| unassigned | 有稳定证据，但尚未绑定 TechnicalProject |
| linked | 已进入某个项目草稿，等待确认 |
| confirmed | 用户确认了部署身份和项目关系 |
| stale | 后续扫描暂时未观察到，保留历史与来源 |
| ignored | 用户要求在本地候选视图中隐藏，外部事实仍保留 |

外部事实只追加新观察；用户决定、项目绑定和忽略规则单独保存。重扫不得静默覆盖已确认关系。

## 4. 多 Provider 发现契约

### 4.1 发现顺序

    SSH / Linux 基线
    → Docker / Compose Provider（可选）
    → systemd Provider
    → PM2 Provider
    → 监听端口与进程 Provider
    → 用户确认根目录的清单/文档 Provider
    → DeploymentCandidate 归并

本轮实际只执行 `docker` / `compose` / `systemd` Provider。用户确认根目录、独立 documents、PM2、端口/进程和 Podman Provider 都属后续增量，不写成已可用。

### 4.2 Provider 结果

每个 Provider 独立返回状态，不因单个 Provider 缺失终止整轮：

    provider_kind
    status = ready | unavailable | permission_denied | timed_out | failed
    observed_count
    evidence_refs[]
    warnings[]
    observed_at

整轮发现状态由 SSH 基线和各 Provider 结果共同组成：

    connection_ready
    discovery_complete
    discovery_partial
    discovery_unavailable

connection_ready 只表达网络、SSH 认证和 Linux 身份可读取，不代表项目完整、服务健康或业务正常。

聚合只依据已执行 Provider 的 `status`，不依据发现数量：

- 所有 Provider 都是 `ready` 时为 `discovery_complete`；
- 至少一个 Provider 是 `ready`、但不是全部 `ready` 时为 `discovery_partial`；
- 没有任何 Provider 是 `ready` 时为 `discovery_unavailable`；
- `status = ready` 且 `observed_count = 0` 表示成功得到空结果，仍按 `ready` 参与聚合，不降级为不可用。

`evidence_ready` 是旧发现记录的兼容成功状态。`evidence_ready`、`discovery_complete` 和 `discovery_partial` 都产生确定性 `ProjectionDraft`，并可在该草稿上启动 Agent 辅助；`discovery_unavailable` 不产生 `draft_id`，也不启动 Agent 辅助。

### 4.3 发现请求

`POST /api/v1/hosts/{host_id}/discovery-runs` 的当前请求体为 `DiscoveryRunCreateRequest`：

```json
{
  "provider_kinds": ["docker", "compose", "systemd"],
  "root_refs": [],
  "requested_capabilities": ["read_only"]
}
```

- `provider_kinds` 当前只接受 `docker`、`compose` 和 `systemd`；产品 UI 默认显式发送 `["docker", "compose", "systemd"]`；
- Docker 与 Compose 当前由同一发现切片采集，显式请求只要包含其中一个，就必须同时包含二者，否则返回 `DISCOVERY_PROVIDER_COMBINATION_UNSUPPORTED`；
- `root_refs` 是后续用户确认根目录 Provider 的保留字段，本轮必须为空，非空请求返回 `DISCOVERY_ROOT_PROVIDER_UNAVAILABLE`；
- `requested_capabilities` 当前只允许 `read_only`，不因请求字段而放开任意命令或写操作；
- 空对象 `{}` 及缺省/空 `provider_kinds` 仅保留为旧客户端兼容路径，走现有 Docker/Compose 自动发现；产品 UI 不使用该路径。

### 4.4 稳定身份与归并

Provider 不能只用显示名称去重。优先使用：

    host_id + provider_kind + external_id

同一个 systemd 服务同时被端口和进程 Provider 观察到时，保留一个 Deployment，挂接多条 Evidence。名称、目录和端口只能作为辅助证据，无法形成稳定身份时保持 unassigned。

## 5. 发现到项目投影

    Provider Evidence
    → DeploymentCandidate
    → ProjectionDraft
    → 用户确认/编辑
    → TechnicalProject
    → Business 绑定
    → ProjectTarget 物化

用户在审查工作台可以：

- 绑定到已有 TechnicalProject；
- 创建新的 TechnicalProject；
- 合并多个部署候选；
- 拆分误合并的候选；
- 将项目挂到已有 Business；
- 忽略候选或保留为未归类。

Agent 只生成建议、理由、证据引用和待回答问题。建议不能绕过用户确认直接生成正式项目关系。

确认后项目资源 URL 使用：

    #scope=project&project=<project_id>&view=resource

全局业务网表达业务、项目和待确认项；项目资源页表达 Deployment、服务、容器和共享引用。

## 6. 服务器页面

### 6.1 页面入口

全局三个视图的职责固定为：

- `#scope=global&view=world`：业务、项目和待确认的业务关系；HOST 不作为业务首屏节点；
- `#scope=global&view=resource`：共享资源集合和资源影响反查；不承载 HOST 登记、重连或发现控件；
- `#scope=global&view=hosts`：服务器资产、连接状态、Provider 覆盖和只读发现操作。

从共享资源的 HOST 引用查看服务器时，显式跳转 `global/hosts`，不把两类控件混在同一首屏。

当前分层已落实到产品 UI，但 `/views/global/world` 底层响应仍暂留 HOST 兼容节点；前端过滤这些节点，并借其 `source_refs` 恢复旧发现投影。下一步先将最新 run/draft 指针移入 hosts 读模型并切换恢复路径，再解耦 world 响应中的 HOST。

### 6.2 页面读模型

服务器总览至少展示：

    host_count
    connection_ready_count
    connection_failed_count
    discovery_partial_count
    stale_evidence_count
    unknown_count

服务器列表至少包含：

    host_id / display_name
    address / port / ssh_user（按现有脱敏规则）
    connection_state
    discovery_state
    provider_coverage[]
    deployment_count
    project_count
    last_observed_at
    freshness
    attention_count

服务器详情包含：

- 主机身份、Linux 基线和最近连接结果；
- Docker、Compose、systemd、PM2 等 Provider 能力矩阵；
- 最近发现批次、失败原因和覆盖范围；
- Deployment 列表及其候选/确认状态；
- 关联 TechnicalProject 和共享资源影响；
- 登记、重连、只读发现、查看证据和跳转项目入口。

### 6.3 监控语义

当前 H1/H2/H3a 已提供最近资源快照、显式 interval 调度和从 schema 11 开始积累的 typed raw 历史；单次 raw 查询最多覆盖 7 天，不从 current 回填，也不自动清理。它仍不等于完整持续健康监控：hour/day compaction、完整 gap/coverage、版本化阈值、健康评价和告警尚未实现；页面本身不替代这些能力，也不把 SSH 成功提升为业务健康。

## 7. Project Agent 的权限与上下文

Project Agent 的直接执行权限放在 TechnicalProject 和 ProjectTarget；Business 保存跨项目约束，不要求存在独立 Business Agent。

    全局硬限制
    ∩ BusinessPolicy
    ∩ ProjectAgentPolicy
    ∩ ProjectTarget.capabilities
    ∩ 本次审批结果

Project Agent 对当前项目范围内的结构化事实拥有完整按需读取权：项目边界、全部 ProjectTarget、Deployment 观察、相关 HOST 能力、共享资源引用、策略和历史回执。原始日志按需检索，不默认复制到 Agent 上下文；跨项目私有数据需显式授权。

首阶段只开放 typed read-only tools，例如：

    list_project_targets
    read_deployment_observation
    read_host_capabilities
    read_service_status
    read_recent_diff

后续任何写入、重启或部署都必须独立声明能力、审批、回执、重新观察和回滚/补偿方式。

## 8. 下一阶段实施顺序

1. 在旧 `Project` 投影契约上完成 Provider 选择、聚合状态与兼容读取。
2. 完成 systemd 发现和 `global/hosts` 服务器资产读模型；将最新 run/draft 指针移入 hosts 读模型并切换旧投影恢复路径后，再解耦 `/views/global/world` 中暂留的 HOST 兼容节点。
3. 实现用户确认根目录 Provider，再按真实样本增加 documents、PM2 和端口/进程 Provider。
4. 补齐 DeploymentCandidate 审查和人工绑定界面。
5. 在用户确认边界后，再从兼容 `Project` 投影迁移到 TechnicalProject / ProjectTarget 模型。
6. 开放项目范围内的 typed read-only Project Agent 工具。

## 9. 验收条件

- Docker 缺失时 HOST 仍保持 connection_ready，其他 Provider 可继续返回结果；
- Provider 聚合符合 complete / partial / unavailable 规则，成功的空结果保持 `ready`；
- `evidence_ready` / `discovery_complete` / `discovery_partial` 产生草稿，`discovery_unavailable` 不产生草稿或 Agent 会话；
- 产品 UI 默认请求 Docker、Compose、systemd，显式 Docker/Compose 必须成对；`{}` 仅保持旧 Docker/Compose 兼容路径，非空 `root_refs` 在根目录 Provider 实现前明确拒绝；
- 一次扫描可以得到多个 DeploymentCandidate，且每项带稳定身份、Evidence、时间、新鲜度和覆盖范围；
- 用户可以合并、拆分、绑定、忽略候选，不会改写外部事实；
- 同一 TechnicalProject 可以绑定多个 HOST 上的 ProjectTarget；
- 全局服务器页面可区分连接、发现、证据新鲜度和业务项目数量；
- `global/world` 不把 HOST 当作业务首屏，`global/resource` 只承担共享资源，HOST 管理只在 `global/hosts`；
- 本轮的草稿与 Agent 继续使用旧 `Project` 投影兼容契约，不伪装为 TechnicalProject / ProjectTarget 已迁移；
- Project Agent 读取项目目标时必须落到具体 ProjectTarget；
- CodeWorkspace、任意 SSH Shell 和远程写操作不进入本阶段交付；
- 完整健康评价尚未实现时，界面只显示最近观测、raw 趋势和 unknown/stale，不生成绿色“持续正常”结论。
