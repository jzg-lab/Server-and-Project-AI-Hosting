# MVP 决策记录

- **状态**：当前产品 MVP-1 基线已确认；开发顺序已按可视化价值重新排序
- **日期**：2026-08-12
- **对应阶段**：`M0 → M1 → M2 → M3 → M4`

> 本文只记录当前 MVP-1 的已确认决策和决策门。MVP-1 是一个完整的产品/技术纵向闭环，不再拆成“技术 MVP”和另一个“产品 MVP”。长期 Agent 责任网络以 `docs/11` 为参考，但不参与当前验收。

## 1. 已确认决策

| 决策项 | 当前结论 |
|---|---|
| 产品主语 | 从可视化管理入手；用户管理 Business、TechnicalProject、Deployment、HOST、资源及其关系 |
| MVP-1 定义 | 一个 Linux HOST 的真实数据进入现有画布，用户可查看、整理、修改、确认、保存并重扫比较 |
| 当前最先开发 | 先固定真实图契约和 DataSource，再完成 SSH 事实链，然后完成无模型也可用的图草稿与人工管理 |
| Agent 的位置 | Agent 在真实图之后辅助归类、解释关系、提问和生成补丁；不是扫描、上图或人工确认的前置条件 |
| 首批真实页面 | 全局业务网、项目资源图 |
| 保留但不阻塞 | 项目流程/运行、共享治理、业务统筹 Agent 工作台和历史轨迹保留当前视觉；其完整真实能力后置 |
| SSH 核心性 | SSH 是 MVP-1 的唯一远程发现路径；没有通过连接与指纹检查就不启动发现 |
| 首版目标主机平台 | 只支持 Linux TARGET_HOST；Windows/macOS 留到后续 |
| SSH 凭据 | MVP-1 默认采用 SSH 账号密码，兼容用户明确提供的 SSH Key；账号密码登录支持标准 Password Authentication 与单密码 Keyboard-Interactive/PAM；不扫描或盲试私钥集合；多因素/MFA、多轮交互、SSH Agent 和托管公钥安装后置 |
| 首次主机指纹 | 服务端取得指纹，界面展示给用户确认；确认前保持 `host_key_unverified` |
| 应用与目标主机 | APP_HOST 运行本系统；TARGET_HOST 是被扫描的 Linux 主机；默认分开记录，允许显式登记为同机 |
| SSH 实现 | Rust 服务端调用系统 OpenSSH；严格 `known_hosts`，固定只读动作，不安装目标机常驻程序 |
| Docker Provider 权限 | 启用 Docker/Compose Provider 时目标 SSH 用户需已有 Docker 只读访问；不自动 `sudo`，且不作为 `connection_ready` 前置条件 |
| 事实来源 | MVP-1 使用 Docker/Compose 与白名单项目文档；下一阶段扩展 systemd、PM2、端口/进程和用户确认目录 Provider |
| 候选语义 | DeploymentCandidate 是发现归并结果；Deployment 是用户确认后的稳定部署实例；ProjectTarget 是项目目标绑定 |
| 服务器页面 | 下一阶段增加 global/hosts 服务器资产与最近观测页，与共享资源反查分开 |
| 初始图生成 | 确定性规则先生成 `projection_draft`；无法确定的归属保持 `unassigned` |
| 模型调用 | OpenAI Chat Completions 兼容；首版非流式，只配置 URL、Key、Model |
| 用户最终决定 | 用户可以采用 Agent 建议，也可以完全手动修改；确认后才发布本地投影 |
| 重新扫描 | 新事实与已确认投影并列比较；不静默覆盖用户归类、布局和忽略规则 |
| 后端基线 | Rust/Axum 模块化单体、SQLite WAL、OpenAPI 生成前端类型、REST 快照/命令、SSE 通知 |
| 部署形态 | Linux APP_HOST，单一所有者，经 HTTPS 互联网访问 |
| 数据保留 | 当前投影、用户决定和审计摘要保留至手动删除；最近 3 次脱敏扫描；原始临时内容最多 24 小时 |
| 凭据处理 | SSH 密码、SSH Key 和模型 Key 只在服务端秘密存储中保存，业务库只保存引用及密码请求的 Argon2id 幂等验证值 |
| 控制动作 | 暂缓；不进入 MVP-1 用户可用路径 |
| 事实边界 | 外部系统仍是事实来源；本地投影不等于外部项目或基础设施被创建/修改 |

## 2. 开发队列

### 2.1 现在做：M0–M2

```text
现有 UI 基线
→ 统一节点/边/状态/来源契约
→ MockDataSource / HttpDataSource
→ HOST + SSH 账号密码（或 SSH Key）+ 指纹确认
→ Docker/Compose/文档只读事实
→ 确定性图草稿
→ 图上人工整理与投影确认
```

这是首个必须打通的纵向切片。完成后，即使模型尚未接入，用户也能从真实服务器形成一张可管理的项目图。

### 2.2 接着做：M3

```text
URL / Key / Model
→ Agent 读取结构化事实与脱敏摘要
→ 建议 / 解释 / 必要问题 / 可编辑补丁
→ 用户采用、拒绝或修改
→ 第二次扫描差异
```

Agent 失败只影响辅助结果，不能让已生成的图草稿消失，也不能阻止人工确认。

### 2.3 发布前补齐：M4

- 单一所有者登录、会话保护、HTTPS、限流和审计；
- SSE 断线恢复、任务重试和最终状态快照；
- 秘密泄露检查、数据导出和删除演练；
- Linux APP_HOST 的安装、启动、备份和恢复说明。

### 2.4 Post-MVP

- 多 Agent 协作、项目责任契约、完整项目脉搏；
- 周期性无人值守监督与复杂告警；
- 流程真实执行、共享知识治理和跨项目协调；
- 外部控制动作、多 HOST、多用户和复杂 RBAC。

## 3. 视图职责与视觉基线

现有前端设计继续保留，不进行视觉重写。MVP-1 只把首批页面换成真实数据并补充状态表达。

### 3.1 首批真实页面

1. **全局业务网**：显示业务、已确认项目、待确认的业务关系和真实空状态，不把 HOST 作为业务首屏。
2. **项目资源图**：显示当前项目的 Compose 服务/容器、网络、卷、端口、文档和关系。

MVP-1 之后的第一条页面增量是 **服务器资产页**：显示 HOST 连接、Provider 发现覆盖、DeploymentCandidate、最近观测和新鲜度。它不改变当前两张 MVP-1 真实页面的验收范围。

关系图/状态图继续是主舞台；文字、错误、来源和操作使用固定信息岛渐进披露。

### 3.2 保留的现有交互

- 全局业务网、全局资源、项目运行与流程、项目资源的导航结构；
- 固定信息岛，不恢复遮挡画布的详情抽屉；
- 节点拖拽时连线、箭头和标签逐帧跟随；
- 运行/编辑模式复用相同节点位置；
- 项目运行轨迹和外部依赖区保持原有布局；
- 当前业务统筹 Agent 节点、工作台和输入区可作为现有视觉元素保留。

保留这些界面不代表 MVP-1 要实现全部后台语义。尚无真实事实支持的区域必须标记为 `fixture`、`unavailable` 或禁用，不能显示为真实健康、真实运行或真实控制能力。

### 3.3 当前不新增的视觉负担

- 不在首屏增加 `ResponsibilityContract`、完整 `ProjectPulse`、多 Agent 状态矩阵；
- 不把项目卡堆成监控仪表盘；
- 不增加复杂权限图、知识图或跨项目委托图；
- 不因未来愿景重新排列已经确定的画布结构。

统一图形语法与视觉验收见 `docs/06-可视化第一性原理与界面规则.md`。

## 4. 项目登记而非项目创建

项目是业务网的一级本地容器，代表用户已经拥有的项目。MVP-1 的登记流程是：

```text
扫描外部事实
→ 确定性规则生成项目/资源草稿
→ 画布立即展示草稿
→ Agent 可选地提出归类建议和问题
→ 用户手动修改或采用建议
→ 用户确认本地投影
```

“本地投影已确认”与“外部项目已创建”是不同状态。服务器购买、域名注册、账号开通、令牌签发、容器修改和部署继续由外部系统或人工负责。

## 5. 事实、映射、建议与决定

MVP-1 必须分开保存四层：

| 层 | 产生者 | 例子 | 是否可直接覆盖下一层 |
|---|---|---|---|
| 发现事实 | SSH 发现器/文档提取器 | Compose 名、容器 ID、网络、卷、文档哈希 | 否 |
| 确定性映射 | 投影映射器 | Compose 项目形成 DeploymentCandidate、容器连接网络 | 只能生成草稿 |
| Agent 建议 | 模型服务 | 两个候选应合并、文档归属冲突、向用户提问 | 否 |
| 用户决定 | 用户 | 更名、移动、合并、忽略、确认 | 是，发布为当前本地投影 |

确定性映射的最小优先级：

```text
Compose project / service 身份
→ Docker 标签和明确引用
→ Compose 工作目录与资源挂载
→ 文档中的明确项目标识
→ 保持未归类
```

Agent 可以解释未归类或冲突，但不能把低置信度推测伪装成确定关系。

### 5.1 下一阶段运维映射

下一阶段把“项目”拆成部署事实与本地关系：

    Provider Evidence
    → DeploymentCandidate
    → 确定性 Deployment 草稿
    → 用户确认 ProjectTarget
    → TechnicalProject / Business 本地投影

Compose project 名称、systemd unit 名称和 PM2 app 名称都是外部身份证据，不直接生成 Business 或 TechnicalProject。ProjectTarget 记录具体 HOST、Deployment、适配器和能力范围。

## 6. Agent 在 MVP-1 中的最小职责

MVP-1 只需要一个内置辅助会话，不建设“业务统筹 Agent + 每项目 Agent”的运行网络。它负责：

- 根据结构化事实和脱敏项目文档提出归类建议；
- 解释建议所依据的来源；
- 对阻塞归类的少量缺失信息向用户提问；
- 生成可预览、可编辑、可拒绝的投影补丁。

它不负责：

- 持续托管项目或承诺项目结果；
- 自动创建项目、修改服务器或控制 Docker；
- 自动发布正式投影；
- 读取完整秘密、环境变量、日志或全量知识库；
- 构建多 Agent 委托、权限和记忆基础设施。

长期逻辑角色见 `docs/11`，不得成为当前后端模块或 API 的前置依赖。

## 7. MVP-1 数据保留默认

保留判断标准是“能否解释当前图、复核用户决定和恢复服务”，不为未来分析无限保存原始内容：

| 数据 | 默认保留 | 删除/压缩方式 |
|---|---|---|
| 当前事实、已确认投影、用户决定、忽略规则、布局、审计摘要 | 直到用户按工作区/HOST/项目删除 | 删除前可导出 |
| 每个 HOST 的扫描结果 | 最近 3 次完整脱敏证据 | 更早记录只保留摘要、哈希、时间和差异 |
| 原始 SSH 输出、完整文档正文、完整模型输入/响应 | 不进入长期库；任务临时目录最多 24 小时 | 到期清理；日志只留脱敏错误摘要 |
| SSH 密码、SSH Key、模型 Key | 只保留服务端 SecretProvider 记录，SQLite 保存引用；密码请求只保存 Argon2id 幂等验证值 | 删除配置时同步清理引用；孤立引用由后续显式清理流程处理 |
| 数据库备份 | 手动导出；不自动上传第三方 | 完成恢复演练后再清理旧备份 |

## 8. 控制动作暂缓

MVP-1 不实现暂停、取消、改向、批准、Docker 修改或其他外部控制动作。首个真实控制对象、权限、成功回执、重读验证和回滚方式尚未确定；提前实现会把“请求已接收”误报为“外部状态已改变”。

当前只保留最小扩展字段，不实现通用动作平台，也不在可用界面中放置看似可执行的控制按钮。

## 9. MVP-1 验收基线

- 默认仍以关系图作为首屏主面积，现有视觉与交互无明显回归；
- 一个 Linux HOST 的真实 Docker/Compose 和文档事实能进入图草稿；
- 模型未配置时，用户仍能查看、修改、确认和保存图；
- 节点与关键关系能看到来源、观察时间和草稿/确认状态；
- 用户能更名、移动、合并、拆分、忽略和归档本地投影；
- Agent 建议带证据，可采用、拒绝或修改；
- 二次扫描能显示变化且不覆盖用户决定；
- Fixture 与真实状态明确区分；
- 目标 HOST 始终保持只读；
- 公网发布前完成所有者认证、HTTPS、秘密边界和恢复验证。

## 10. 下一决策门

以下四项已经锁定，不再作为分歧项：SSH 是核心入口、TARGET_HOST 只支持 Linux、默认使用 SSH 账号密码并兼容 SSH Key、首次指纹由服务端展示并由用户确认。

进入 M1/M2 前需要从真实样本确认：

1. 首个 TARGET_HOST 的 Docker/Compose 版本、rootless 模式和可用只读权限；
2. 文档白名单、单文件上限、总文件数和总大小；
3. 首批图中各类 Docker 事实到节点/关系的精确映射；
4. 同一容器被多个 Compose/DeploymentCandidate 引用时的默认展示方式；
5. 首个真实样本图规模及可接受的快照/布局性能。

进入 M4 前再确认：

6. 反向代理、域名、HTTPS 和所有者登录方案；
7. 模型中转是否需要自定义请求头或路径；
8. 默认保留策略是否需要除按工作区/HOST/项目删除以外的入口。
